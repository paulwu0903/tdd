# Rule 1 - 三類決策要向使用者提問 [MUST]
- 會改變 spec 範圍、會改變使用者可見行為、或取決於使用者偏好的決策，都要逐題附選項與權衡向使用者提問，不自行定案。
- 純技術選型（框架、套件、演算法、儲存方式）由查證事實決定，不提問。

## Good Example
- HEIC 是否支援會改變使用者可見行為（部分照片能不能匯入），列為提問；縮圖用哪個 API 是純技術選型，直接決定。

```
提問：iOS 以外的瀏覽器不支援 HEIC 時，要（A）隱藏這些照片並提示，或（B）引入轉檔套件？
不提問：縮圖以 createImageBitmap 搭配 OffscreenCanvas 產生
```

## Bad Example
- 「不支援 HEIC 就靜默略過」改變了使用者看到的匯入結果，卻當成技術選型自行決定。

```
R8. HEIC 支援
- Decision: 不支援的瀏覽器靜默略過 HEIC 檔案
```

# Rule 2 - UI 外觀留給 ui-plan [MUST]
- 主題範圍、配色、字型、版面風格屬使用者偏好，不在 research 決策內，由 ui-plan 向使用者取得。
- 技術上必須提及外觀時，只寫機制（例如「色彩以 CSS 自訂屬性定義」），不寫範圍（例如「提供淺色 / 深色」）。

## Good Example
- 樣式決策只寫機制，主題範圍留給 ui-plan。

```
R11. 樣式
- Decision: 純 CSS，CSS Modules 搭配 :root 自訂屬性定義色彩與間距；主題範圍由 ui-plan 依使用者偏好決定
```

## Bad Example
- 在樣式決策裡順手定了主題範圍，之後 ui-plan 問到使用者只要深色，兩份文件衝突。

```
R11. 樣式
- Decision: 純 CSS，CSS Modules 搭配 :root 自訂屬性，並以 prefers-color-scheme 提供淺色 / 深色
```

# Rule 3 - 目錄結構留給 system-analysis [MUST]
- research 只寫套件、機制與模組邊界，不寫工作區切分、目錄與檔案路徑；那是 system-analysis 在 plan.md 的 Source Code 樹的職責。
- 需要指稱某個模組時以角色描述，並註明「落點依 plan.md」。

## Good Example
- 只講模組邊界與機制，落點交給 plan.md。

```
R9. 縮圖產生
- Decision: 以 createImageBitmap 搭配 OffscreenCanvas 產生，獨立成不依賴 DOM 的模組，供匯入流程與測試共用；落點依 plan.md
```

## Bad Example
- 在 research 裡定了套件切分與檔案路徑，之後 plan.md 另定一棵樹，兩份文件各說各話。

```
R9. 縮圖產生
- Decision: 以 createImageBitmap 搭配 OffscreenCanvas 產生，放在 packages/core/src/thumbnail.ts，由 packages/web 以 workspace 引用
```
