# Rule 1 - 版本與相容資訊取自當下的官方來源 [MUST]
- 版本、相依需求、瀏覽器支援、授權與發佈日，一律在撰寫當下向官方來源查詢，不使用訓練資料中的記憶。
- 各類資訊的官方來源依下表選擇：

| 資訊 | 官方來源 |
|---|---|
| 套件版本、`peerDependencies`、`engines`、授權、發佈日 | 套件的 registry（如 `https://registry.npmjs.org/<套件>`） |
| 執行環境版本與 LTS 狀態 | 官方發佈索引（如 `https://nodejs.org/dist/index.json`） |
| 瀏覽器 API 支援版本 | MDN browser-compat-data |
| 函式庫的行為細節 | 官方 repository 的文件或原始碼 |

## Good Example
- 從 registry 查到 npm latest 是 7.0.2，並記下 typescript-eslint 的 peer 範圍。

```
- **TypeScript 7.0.2（npm latest）**：`typescript-eslint` 8.72.0 的 peer dependency 為
  `typescript >=4.8.4 <6.1.0`，尚不支援 7.x；
```

## Bad Example
- 版本憑記憶填寫，撰寫當下的最新版早已不是 5.x。

```
- **Decision**: TypeScript 5.x（目前最新版）+ React 18。
```

# Rule 2 - 選定的依賴要互相交叉檢查相容性 [MUST]
- 每個選定的套件都要檢查它的 `peerDependencies` 與 `engines`，是否和其他選定套件、選定的執行環境版本相容。
- 不相容時，改選相容的版本，並在 Alternatives 寫明被排除的版本與原因。

## Good Example
- 交叉檢查後發現 TS 7 不相容，固定 6.0.x；jsdom 的 `engines` 決定了 Node 版本。

```
- **Decision**: TypeScript 6.0.3（`strict: true`）+ React 19.3.1 + Vite 8.3.5
...
- **Rationale**: jsdom 30.1.3 要求 `^22.22.2 || ^24.15.0 || >=26`；Vitest 5 與 Vite 8 皆相容。
```

## Bad Example
- 各套件都選了最新版，卻沒有檢查彼此相容，安裝後 typescript-eslint 會報 peer 衝突。

```
- **Decision**: TypeScript 7.0.2 + ESLint 10.13.0 + `typescript-eslint` 8.72.0。
```

# Rule 3 - 判斷維護狀態時附最後發佈日 [SHOULD]
- 以「是否仍在維護」作為取捨理由時，要寫出 registry 上的最後發佈日期。
- 最後發佈日以 registry 的 `time[<latest 版本>]` 為準；`time.modified` 是 metadata 的修改時間，不是發佈日。
- 只寫「不再維護」卻沒有日期，讀者無法查證，也無法判斷之後是否改變。

## Good Example
- 寫出最後發佈的年月，可以直接在 registry 驗證。

```
- **Alternatives considered**: `exifr` 7.1.3 速度快且廣泛使用，但最後一次發佈為 2021-08，
```

## Bad Example
- 只有結論，沒有日期。

```
- **Alternatives considered**: `exifr` 已經沒人維護，否決。
```

# Rule 4 - 每項事實都要在 Sources 找得到出處 [MUST]
- research.md 中的每個版本、相容性與行為描述，都要能對應到 Sources 中的某個 URL。
- 來自原始碼的行為描述，Sources 要標出套件版本與查到的內容。

## Good Example
- `setInputFiles` 的行為來自原始碼，Sources 標出版本與查到的內容。

```
- https://registry.npmjs.org/playwright-core/1.64.1 （原始碼：`setInputFiles` 以檔案路徑上傳時帶上 `mtimeMs`，
  FilePayload 支援 `lastModifiedMs`）
```

## Bad Example
- R5 寫了 Safari 的支援版本，Sources 卻沒有任何瀏覽器相容性資料的來源。

```
R5：主執行緒的 `FileSystemFileHandle.createWritable()` 在 Safari 需 26 版
## Sources
- https://registry.npmjs.org/
```

# Rule 5 - 官方來源無法確定時才以實測確認，並記錄可重現的做法 [MUST]
- 只有 registry、官方文件與原始碼都無法確定的行為（例如預建二進位檔是否支援某種格式），才以實際執行來確認。
- 實測結果要在 Sources 寫出套件版本與可重現的指令，讓讀者能自行重跑驗證。

## Good Example
- 寫出版本與指令，讀者可以重跑。

```
- 實測（sharp 0.35.5 預建版本）：`node -e "require('sharp')('sample.heic').toBuffer().catch(e => console.log(e.message))"`，
  輸出解碼失敗訊息，確認預建版本不支援 HEIC
```

## Bad Example
- 寫了實測的結論，Sources 卻沒有版本和指令，無從驗證，也不知道換版本之後是否還成立。

```
R11：sharp 預建版本無法解碼 HEIC（已測試）。
## Sources
- https://registry.npmjs.org/sharp
```
