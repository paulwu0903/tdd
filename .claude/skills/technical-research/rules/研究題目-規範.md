# Rule 1 - 一題只裝一個決策 [MUST]
- 一個 R 節只回答一個技術決策；兩個決策互不約束、可以各自單獨替換時，拆成兩題。
- 判準：換掉其中一個方案後，另一個的選擇完全不受影響，就是兩個決策；互相綁定的選擇放在同一題。

## Good Example
- 路由和照片匯入互不約束，分成兩題；語言、框架與建置工具互相綁定（`@vitejs/plugin-react` 綁定 React、TypeScript 版本受 `typescript-eslint` 限制），放在同一題。

```
## R2. 語言、框架與建置工具
## R3. 路由
## R4. 照片匯入方式
```

## Bad Example
- 路由和匯入綁在同一題，換掉其中一個方案時，整節的 Rationale 和 Alternatives 都要重寫。

```
## R3. 路由與照片匯入
```

# Rule 2 - 刻意不引入套件也算一個決策 [SHOULD]
- 選擇自己實作或不用任何函式庫時，同樣要開題，寫明不引入的理由和被否決的套件。
- 不開題的話，實作者會自行補上套件，研究結論等於沒有定案。

## Good Example
- 決定不用 i18n 套件，仍然開題說明為什麼。

```
## R14. 文案與 i18n

- **Decision**: 不引入 i18n 套件；所有文案集中於 `src/i18n/zh-TW.ts`，以型別化的 `t(key, params)` 取用。
- **Rationale**: 文案集中一處便於校對與日後擴充語系；v1 只有一種語系，引入完整 i18n 函式庫屬過早抽象。
```

## Bad Example
- 因為「沒有選任何套件」就沒有開題，研究文件對文案管理完全沒有說法。

```
## R13. 平鋪檢視與虛擬捲動
## R15. 測試與品質工具
（沒有任何一題處理文案與 i18n）
```

# Rule 3 - 題目依固定順序排列 [SHOULD]
- 依序為：應用程式形態 → 語言、框架與建置工具 → 各功能別的決策 → 跨領域品質（測試、執行環境、啟動、部署與網路設定、安全、效能、決定性）。
- 前面的決策會限制後面的選項，讀者由上往下讀時才不必回頭找前提。

## Good Example
- 先定形態與技術棧，再定功能，最後才是測試與效能。

```
## R1. 應用程式形態
## R2. 語言、框架與建置工具
## R3. 路由
...
## R14. 文案與 i18n
## R15. 測試與品質工具
## R16. 執行環境
## R17. 內容安全政策（CSP）與「資料不上傳」的驗證
## R18. 效能量測與回歸檢查
## R19. 測試的決定性
```

## Bad Example
- 測試工具排在最前面，讀者還不知道用什麼框架，就看不懂為什麼選 `@testing-library/react`。

```
## R1. 測試與品質工具
## R2. 應用程式形態
## R3. 語言、框架與建置工具
```

# Rule 4 - spec 中有技術含義的需求都要有題目涵蓋 [MUST]
- spec 的每條 FR、NFR、Success Criteria、Edge Case 與 Assumption，只要實作時需要做技術選擇，就至少要有一題處理。
- 不需要做技術選擇的需求（純業務規則、文案內容）不必開題。
- 需求與題目的對照只用於撰寫時的自我檢查，不寫進 research.md。

## Good Example
- 每條有技術含義的需求，都能指到處理它的題目。

```
FR-001 選取多張照片或整個資料夾   → R4 照片匯入方式
FR-018 資料不上傳至外部服務       → R1 應用程式形態、R17 CSP 驗證
SC-003 200 張相簿首屏 1 秒內      → R13 平鋪檢視與虛擬捲動
邊界情況「以當地拍攝時間判定日期」 → R7 日期判定與時區
```

## Bad Example
- FR-018 沒有任何一題處理，實作者可能自行選擇雲端儲存，直接違反規格。

```
FR-001 選取多張照片或整個資料夾   → R4 照片匯入方式
FR-018 資料不上傳至外部服務       → （沒有題目）
```
