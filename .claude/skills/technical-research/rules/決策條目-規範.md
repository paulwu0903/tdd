# Rule 1 - Decision 寫到可以直接動手 [MUST]
- 套件與工具寫出精確到 x.y.z 的版本；涉及數值的設定寫出具體數值。
- 判準：實作者照著 Decision 就能開始寫程式，不需要再做任何選擇。

## Good Example
- 尺寸、格式、品質、fallback 都寫死，實作者不必再決定。

```
- **Decision**: 在 Web Worker 中以 `createImageBitmap` + `OffscreenCanvas` 產生最長邊 400px 的 WebP
  縮圖（不支援 WebP 編碼時改用 JPEG），品質 0.8。
```

## Bad Example
- 沒有尺寸、格式與品質，版本只寫到大版本，實作者還得自己再決定一次。

```
- **Decision**: 用 Canvas 產生適當大小的縮圖，搭配 React 19。
```

# Rule 2 - Rationale 只以 spec、使用者釐清、查證事實與憲法為依據 [MUST]
- 理由要能對回 spec 的條目（FR、NFR、SC、Edge Case、Assumption）、使用者在釐清時的回答、Phase 2 查證得到的事實，或 `.claude/constitution/` 的條款；引用憲法時寫出檔案與 Rule 編號。
- Decision 中的具體數值若沒有直接依據，可以用由上述依據推導出的工程判斷，但要寫出推導，例如「400px 足以支援高 DPI 下約 200px 的格子」。
- 不引用上述以外的專案原則，也不以「業界主流」「大家都用」當理由。

## Good Example
- 一個指向 spec 的 FR-018 與 Assumptions，一個指向憲法的檔案與 Rule 編號。

```
- **Rationale**: 規格 FR-018 要求資料只存在使用者裝置且不上傳；v1 為單一使用者、無帳號（Assumptions）。
- **Rationale**: 憲法 `skills/technical-research/research.md` Rule 1 規定資料庫一律使用 MySQL。
```

## Bad Example
- 一個引用不存在於輸入中的專案原則，一個只說是主流，兩者都無法追溯。

```
- **Rationale**: 依專案原則 III 的要求。
- **Rationale**: React 是業界主流框架。
```

# Rule 3 - 補充欄只用於相容性與注意事項 [SHOULD]
- 補充欄（`- **<標籤>**：`）只放兩類內容：某個平台或版本的相容性處理，以及執行時要留意的限制。
- 背景知識或重複 Rationale 的內容不另開補充欄。
- 授權義務寫在 Rationale 與依賴授權表，不另開「授權」補充欄。

## Good Example
- 一個是平台相容性的處理，一個是量測的限制。

```
- **iOS 相容性**：iOS Safari 18.4 才支援 `webkitdirectory`，因此以
  `'webkitdirectory' in document.createElement('input')` 偵測，不支援時隱藏「選擇資料夾」，
- **注意**：時間類的指標仍有波動，因此每項量測執行 3 次取中位數再與 baseline 比較。
```

## Bad Example
- 補充欄寫的是 IndexedDB 的背景介紹，和這個決策的取捨無關。

```
- **背景**：IndexedDB 是瀏覽器內建的 NoSQL 資料庫，由 W3C 制定。
```

# Rule 4 - 修訂過 spec 的決策要在 R 節註明 [MUST]
- 經使用者同意修改 spec.md 後，在對應 R 節寫明修訂了哪一條。
- 不註明的話，讀者看到 research.md 與舊版 spec 不一致時，無從得知是哪一份過時。

## Good Example
- 寫明 FR-001 已同步修訂。

```
  保留 Safari 17+ 的支援範圍（spec.md FR-001 已同步修訂）。
```

## Bad Example
- spec.md 已被改過，R4 卻完全沒提到。

```
- **iOS 相容性**：不支援時隱藏「選擇資料夾」，保留 Safari 17+ 的支援範圍。
```

# Rule 5 - 每個替代方案都要寫出理由與結論 [MUST]
- 每個替代方案寫出名稱（有版本則附版本）、不採用的理由，以及結論：「否決」或「延後」。
- 結論為延後時，要寫出什麼條件下會重新評估。

## Good Example
- 一個否決、一個延後，延後的寫出重新評估的條件。

```
  - **localStorage**：容量約 5 MB 且只能存字串，否決。
  - **OPFS（Origin Private File System）存 Blob**：大檔效能較佳；但主執行緒的
    `FileSystemFileHandle.createWritable()` 在 Safari 需 26 版，跨瀏覽器寫入需改走 Worker 的
    `createSyncAccessHandle()`，增加複雜度。v1 先用 IndexedDB，若量測顯示大量匯入時寫入成為瓶頸再遷移。
```

## Bad Example
- 只說可行，沒有不採用的理由，也沒有結論。

```
  - **Svelte / Vue**：可行。
```

# Rule 6 - 沒有合理的替代方案才省略 Alternatives [SHOULD]
- 有曾被考慮或可能被提出的候選方案時，一律寫出 Alternatives considered。
- 查證時因相容性而排除的版本，也算考慮過的候選，必須寫進 Alternatives。
- 決策直接由 spec 決定、或已由前面的 R 節決定時，可以省略。

## Good Example
- R7 的做法由 spec 的邊界情況直接決定，沒有其他合理做法，省略 Alternatives。

```
## R7. 日期判定與時區

- **Decision**: EXIF `DateTimeOriginal` 為不含時區的當地時間，直接取其 `YYYY-MM-DD` 作為 `dateKey`，
  **不做時區換算**；
- **Rationale**: 對應規格邊界情況「以照片記錄的當地拍攝時間判定日期，不換算成裝置時區」，
```

## Bad Example
- 查證時明明比較過 TS 7.0.2，卻省略了 Alternatives，讀者會以為沒有考慮過最新版。

```
## R2. 語言、框架與建置工具

- **Decision**: TypeScript 6.0.3（`strict: true`）+ React 19.3.1 + Vite 8.3.5
- **Rationale**: 使用者熟悉 TypeScript / React；
```

# Rule 7 - 只引用已存在的檔案 [MUST]
- 可以引用的對象只有本文件中的其他 R 節，以及撰寫當下已經存在的檔案。
- 要引用的內容所在的檔案還不存在時，把內容直接寫在 R 節內。
- Decision 要求實作時才建立的檔案（如 `THIRD-PARTY-NOTICES.md`）屬於決策內容，不算引用。

## Good Example
- CSP 內容直接寫在 R17；R8 引用的是本文件的 R17。

```
  注入 CSP meta：`default-src 'self'; script-src 'self'; ... connect-src 'self'; ...`。
  - 預設版本需要放寬 CSP；改用 `heic-to/csp` 可以維持嚴格的 `script-src 'self'`（見 R17）。
```

## Bad Example
- 引用了一份還沒產生的檔案，讀者點進去什麼都沒有。

```
  注入 CSP meta（內容見 [ui-contract.md](./contracts/ui-contract.md) 的「隱私與安全」）。
```
