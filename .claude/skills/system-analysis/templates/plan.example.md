**Structure Decision**: 第一層依可獨立建置的 `前端端點`、`後端端點` 切成 `frontend/`、`backend/`；`資料庫端點` 不自成程式專案，資料表定義與交易檔案放在存取它的 `backend/db/` 與 `backend/src/db/`。端點下依角色分層（pages、components、routes、realtime、services、domain、lib、tests），讓同類檔案放在一起，並把謎底比對與勝負判定集中在不依賴網路與時間的 domain 層、把時間來源集中在可注入的 lib 層；每個程式檔的說明標明對應的系統介面，介面的分析結果因此都能找到實作落點，也能反查每個介面由哪些檔案實作。

## 分析流程規劃

### 系統介面的盤點

本次需求共盤點出 `14` 個系統介面。

1. `前端共通介面`
    - 端點類型：`前端端點`
    - 主要介面：匿名玩家識別的瀏覽器保存、連線中斷提示與自動重連、未確認操作的復原、各畫面四態共通規範、錯誤訊息呈現、無障礙、響應式版面、效能預算、在地化文案與日期時間格式
    - 需求原文依據：使用者描述要求「全線上的 PVP 的一個 1A2B 猜數字的遊戲 所以它是一個線上平臺」，需求要求連線中斷時提示並自動重連、各畫面實作四態，且介面符合無障礙、相容性與效能要求；對應 `FR-019`、`FR-026`、`FR-027`、`NFR-007`、`NFR-008`、`NFR-009`、`NFR-010` 與 `NFR-011`。

2. `首頁介面`
    - 端點類型：`前端端點`
    - 主要介面：暱稱輸入與記憶、單一房號輸入入口、房號格式預檢、房間已滿或對戰中提示、已在其他房間的離開提示、輸入頻率超限提示、房間解散通知、首頁四態
    - 需求原文依據：使用者描述要求「玩家在這個平臺上開一個房間 四個號碼 開個房間 另外一個玩家呢 用四個號碼只要比對到了 就可以加入 沒有比對到就是開新的房間」；對應 `FR-001`、`FR-002`、`FR-003`、`FR-004`、`FR-005`、`FR-018`、`FR-019`、`NFR-019` 與 `NFR-021`。

3. `房間介面`
    - 端點類型：`前端端點`
    - 主要介面：房號與等待對手狀態、雙方暱稱與準備狀態、謎底設定與取消準備、房主專屬的開始對戰、離開房間、等待逾時解散提示、房間四態
    - 需求原文依據：使用者描述要求「準備好之後房主開房然後開始」；對應 `FR-005`、`FR-006`、`FR-007`、`FR-019`、`NFR-005` 與 `NFR-021`。

4. `對局介面`
    - 端點類型：`前端端點`
    - 主要介面：輪到者與剩餘秒數、送出猜測與格式提示、xAyB 回饋、雙方猜測紀錄、逾時紀錄、對手斷線倒數、認輸與二次確認、伺服器中止通知、回合變更報讀提示、對局四態
    - 需求原文依據：使用者描述要求「開始 1A2B 兩個人互相猜對方的答案」；對應 `FR-008`、`FR-009`、`FR-010`、`FR-011`、`FR-014`、`FR-015`、`FR-016`、`FR-019`、`NFR-009` 與 `NFR-020`。

5. `結果介面`
    - 端點類型：`前端端點`
    - 主要介面：勝 / 負 / 平手與原因、雙方謎底、雙方完整猜測紀錄、回首頁入口、不提供同房再戰
    - 需求原文依據：需求要求對局結束時雙方看到勝負與原因、雙方謎底與完整紀錄，且不提供同房再戰；對應 `FR-012`、`FR-013` 與 `FR-017`。

6. `戰績介面`
    - 端點類型：`前端端點`
    - 主要介面：總場數、勝負平、勝率、獲勝平均猜測次數、最近 20 場明細、不提供排行榜與他人戰績、戰績四態
    - 需求原文依據：需求要求首頁提供綁定此瀏覽器的「我的戰績」，顯示統計與最近對局明細；對應 `FR-020`、`FR-024`、`FR-025` 與 `NFR-011`。

7. `後端共通介面`
    - 端點類型：`後端端點`
    - 主要介面：請求身分與資料格式驗證、錯誤碼與不曝露內部資訊的回應、加密傳輸、啟動時檢查必要相依服務、健康檢查、營運事件紀錄與謎底不入日誌、即時效能與容量目標
    - 需求原文依據：需求要求伺服器拒絕格式不符的資料、錯誤訊息不曝露內部資訊、啟動時檢查相依服務並提供健康檢查，且在 1,000 場同時對局下維持即時回饋；對應 `NFR-001`、`NFR-003`、`NFR-004`、`NFR-008`、`NFR-012`、`NFR-013`、`NFR-017` 與 `NFR-018`。

### 分析流程的安排

#### Wave 1

- 平行分析端點：
    - `後端端點`
- 安排理由：後端資源與即時事件都能直接由使用者描述與 `spec.md` 的功能需求推出，不需要等待其他端點的分析結果。
- 委派 skill：
    - `後端端點` → `api-plan`

#### Wave 2

- 平行分析端點：
    - `前端端點`
    - `資料庫端點`
- 安排理由：前端畫面要引用 `後端端點` 的 API 與事件，資料表內容與交易邊界取決於各 API 與結算流程的讀寫操作，因此都排在 Wave 1 之後；兩者之間沒有依賴，可平行分析。
- 委派 skill：
    - `前端端點` → `ui-plan`
    - `資料庫端點` → `data-plan`
