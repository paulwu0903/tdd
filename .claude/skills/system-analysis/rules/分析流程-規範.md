# Rule 1 - Wave 只列端點 [MUST]
- 每個 wave 的「平行分析端點」只列端點類型，不列個別系統介面；端點底下的介面隨端點一起分析。
- 端點類型的寫法與系統介面的盤點中的「端點類型」一字不差。

## Good Example
- 只列兩個端點，名稱與盤點中的端點類型相同。

```
- 平行分析端點：
    - `前端端點`
    - `後端端點`
```

## Bad Example
- 把十一個介面逐一列進 wave，規劃細到介面層級。

```
- 平行分析介面：
    - `前端共通介面`
    - `主頁面介面`
    - `相簿頁面介面`
    ……
```

# Rule 2 - 依依賴分層 [MUST]
- 依賴的定義：端點 A 的介面內容必須等端點 B 的介面分析完才能決定，或 A 的產出要引用 B 的產出時，A 依賴 B。前端畫面規格要引用後端契約的 operationId 與事件名稱，因此前端端點依賴後端端點。
- 沒有依賴的端點排在 Wave 1；其餘端點排在其全部依賴所在 wave 的下一個 wave；同一 wave 的端點之間不得有依賴。
- 每個盤點出的端點都必須排入某個 wave，不得遺漏。

## Good Example
- 後端直接由需求推出，排在 Wave 1；前端要引用後端契約，資料表與檔案配置要由後端 API 的讀寫操作推出，三者都排在後端之後，彼此沒有依賴，同在 Wave 2。

```
#### Wave 1
- 平行分析端點：`後端端點`
#### Wave 2
- 平行分析端點：`前端端點`、`資料庫端點`、`檔案儲存端點`
```

## Bad Example
- 資料庫端點依賴後端端點，卻排在同一個 wave 平行分析，分析資料庫時還不知道 API 需要哪些讀寫。

```
#### Wave 1
- 平行分析端點：`後端端點`、`資料庫端點`
#### Wave 2
- 平行分析端點：`前端端點`、`檔案儲存端點`
```

# Rule 3 - 安排理由寫出依賴 [SHOULD]
- 以一兩句說明本 wave 的端點依賴哪個端點（或直接由需求推出），以及同 wave 端點之間為何沒有依賴。
- 不逐一列出介面之間的對應關係。

## Good Example
- 一句說明依賴來源與同 wave 無依賴。

```
- 安排理由：資料表與檔案配置取決於 `後端端點` 各 API 的讀寫操作，因此排在 Wave 1 之後；兩者之間沒有依賴，可平行分析。
```

## Bad Example
- 逐一列出每張表對應哪個 API，篇幅變長卻沒有說明 wave 的劃分依據。

```
- 安排理由：albums 資料表介面依相簿 API 介面、photos 資料表介面依照片 API 介面、原檔儲存介面依照片 API 介面與匯出 API 介面……
```
