# Rule 1 - Documentation 列出本流程的全部文件 [MUST]
- Documentation 樹的根是 spec.md 所在的功能目錄，列出 `spec.md`、`research.md`、`techstack.md`、`plan.md`，以及 `analysis/` 底下 Phase 3 各委派 skill 的產出檔。
- 每個檔案以 `# 說明` 寫出內容與產出它的 skill；委派 skill 的產出檔名取自該 skill 的 SKILL.md，不自行命名。
- 不列不由上述 skill 產出的文件。

## Good Example
- 上游文件與各委派 skill 的產出都列出，每檔註明產出者。

```
specs/001-photo-album-organizer/
├── spec.md                   # 功能規格（/specify 產出）
├── research.md               # 技術決策（/technical-research 產出）
├── techstack.md              # 技術堆疊（/technical-research 產出）
├── plan.md                   # 本檔案
└── analysis/
    ├── frontend.md           # 前端端點的畫面規格（ui-plan 產出）
    ├── openapi.yaml          # 後端端點的 HTTP API 契約（api-plan 產出）
    └── schema.dbml           # 資料庫端點的資料表契約（data-plan 產出）
```

## Bad Example
- 漏列 research.md、techstack.md 與委派 skill 的產出，卻列出 `data-model.md`、`contracts/` 等不知由誰產出的文件。

```
specs/001-photo-album-organizer/
├── spec.md
├── plan.md
├── data-model.md
└── contracts/
```

# Rule 2 - Structure Decision 說明切分理由 [SHOULD]
- 以一段話說明第一層依什麼切分、端點下依什麼分層、檔案如何對回系統介面，以及這樣切對分析與實作的好處。
- 不重述目錄樹本身。

## Good Example
- 說明切分依據、檔案與介面的對應方式與好處，沒有逐一列目錄。

```
**Structure Decision**: 第一層依 `前端端點`、`後端端點` 切成兩個可獨立建置的專案，端點下依角色分層（routes、services、storage、lib、tests），讓同類檔案放在一起；每個程式檔的說明標明對應的系統介面，介面的分析結果因此都能找到實作落點。
```

## Bad Example
- 只把目錄樹再念一次，沒有說明為什麼這樣切。

```
**Structure Decision**: 有 frontend、backend 兩個目錄，backend/src 底下有 routes、services、storage、lib。
```

# Rule 3 - Source Code 樹列出每個資料夾內的檔案 [MUST]
- Source Code 樹精確列出每個資料夾裡有哪些檔案，包含 repository root 與各端點層的設定檔，不只列目錄。
- 每個檔案後以 `# 說明` 簡述它負責什麼；目錄只在需要說明時才加註記。

## Good Example
- root 設定檔、端點層設定檔與程式檔都列出，每個檔案都有簡短說明。

```
package.json                     # 整個 repository 的工作區與共用指令
backend/
├── package.json                 # 後端套件設定與指令
└── src/
    ├── server.ts                # 啟動檢查與啟動伺服器（後端共通介面）
    └── routes/
        └── albums.ts            # 相簿的建立、改名、刪除（相簿 API 介面）
```

## Bad Example
- 只列到目錄，看不出每個目錄裡有哪些檔案、各自做什麼。

```
backend/                         # 後端端點
├── common/                      # 後端共通介面
└── albums/                      # 相簿 API 介面
```

# Rule 4 - 說明只寫職責，不寫實作細節 [MUST]
- 檔名寫出副檔名，資料夾與檔名不帶框架或套件名稱。
- 說明只寫這個檔案負責什麼；框架、套件、API 路徑與欄位、函式呼叫、演算法等實作細節，留給 wave 分析時委派的 skill 決定。

## Good Example
- 檔名有副檔名，說明只寫職責。

```
├── db/
│   └── client.ts                # 資料庫連線與交易（資料庫共通介面）
├── routes/
│   └── photos.ts                # 照片上傳、移動、刪除（照片 API 介面）
```

## Bad Example
- 資料夾帶了 ORM 名稱，說明寫出建構方式與 API 路徑，提前做了 wave 才該做的分析。

```
├── prisma/
│   └── client.ts                # new PrismaClient({ adapter })；單例，關閉時 $disconnect
├── routes/
│   └── photos.ts                # /api/photos*（multer 上傳、sharp 產生縮圖）
```

# Rule 5 - 端點下依角色分層 [MUST]
- 第一層一個目錄對應一個可獨立建置的端點（例如 `frontend/`、`backend/`，root 的設定檔除外）；資料庫、檔案儲存等不自成程式專案的端點，其檔案放在存取它的端點底下（例如 `backend/db/`、`backend/src/storage/`），以 Rule 6 的介面標註對回。
- 端點下依角色分層，例如 `src/routes/`、`src/services/`、`src/lib/`、`tests/`，不再為每個系統介面開一個目錄。

## Good Example
- 端點下依 routes、services 分層，相簿與照片的檔案分散在各自的角色目錄。

```
backend/
└── src/
    ├── routes/
    │   ├── albums.ts            # 相簿的建立、改名、刪除（相簿 API 介面）
    │   └── photos.ts            # 照片上傳、移動、刪除（照片 API 介面）
    └── services/
        └── album-service.ts     # 相簿日期推導與封面設定（相簿 API 介面）
```

## Bad Example
- 端點下為每個系統介面各開一個目錄，與角色分層的結構不符。

```
backend/
├── common/                      # 後端共通介面
├── albums/                      # 相簿 API 介面
└── photos/                      # 照片 API 介面
```

# Rule 6 - 程式檔註明對應的系統介面 [MUST]
- 每個程式檔（含測試檔）的說明以全形括號標出它對應的系統介面，名稱與系統介面的盤點一字不差；同時服務多個介面時以頓號列出。
- `package.json`、`tsconfig.json` 等設定檔不需標註介面。

## Good Example
- 介面名稱與盤點一字不差，設定檔不標註。

```
├── package.json                 # 後端套件設定與指令
├── src/routes/photos.ts         # 照片上傳、移動、刪除（照片 API 介面）
└── src/storage/file-store.ts    # 檔案路徑安全與寫入（原檔儲存介面、衍生圖儲存介面）
```

## Bad Example
- 第一個檔案沒有標出介面；第二個寫成盤點中不存在的「照片模組」。

```
├── src/routes/photos.ts         # 照片上傳、移動、刪除
└── src/services/photo-service.ts # 照片移動與刪除（照片模組）
```

# Rule 7 - 每個系統介面至少對應一個檔案 [MUST]
- 盤點出的每個系統介面，都必須出現在至少一個程式檔的介面標註中。
- 找不到對應檔案的介面，代表漏了檔案，回頭補上。

## Good Example
- 盤點的三個後端介面都能在某個檔案的標註中找到。

```
盤點：後端共通介面、相簿 API 介面、匯出 API 介面
├── src/server.ts                # 啟動檢查與啟動伺服器（後端共通介面）
├── src/routes/albums.ts         # 相簿的建立、改名、刪除（相簿 API 介面）
└── src/routes/export.ts         # 匯出下載（匯出 API 介面）
```

## Bad Example
- 盤點有「匯出 API 介面」，Source Code 樹卻沒有任何檔案標註它。

```
盤點：後端共通介面、相簿 API 介面、匯出 API 介面
├── src/server.ts                # 啟動檢查與啟動伺服器（後端共通介面）
└── src/routes/albums.ts         # 相簿的建立、改名、刪除（相簿 API 介面）
```
