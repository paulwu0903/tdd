# Rule 1 - 介面依功能拆分 [SHOULD]
- 每個端點依功能拆成多個系統介面，不以「一個端點一個介面」交差。
- 拆分依據依端點類型決定：

| 端點類型 | 拆分依據 |
|---|---|
| 前端端點 | 頁面或使用流程 |
| 後端端點 | API 資源 |
| 資料庫端點 | spec.md Key Entities 對應的資料表 |
| 檔案儲存端點 | 檔案類別 |

- 表中沒有的端點類型（硬體、手機、雲端、第三方等），比照最接近的類型拆分；功能單一的端點可以只有一個介面，並在主要介面說明。

## Good Example
- 後端依 API 資源拆成五個介面，每個介面的範圍互不重疊。

```
7. `相簿 API 介面`
8. `照片 API 介面`
9. `排序 API 介面`
10. `影像 API 介面`
11. `匯出 API 介面`
```

## Bad Example
- 整個後端只盤點出一個介面，後續分析無法平行，也看不出各資源的責任邊界。

```
2. `HTTP API 介面`
    - 端點類型：`後端端點`
    - 主要介面：相簿、照片、排序、影像、匯出的所有 API
```

# Rule 2 - 共通介面只承接跨功能需求 [SHOULD]
- 端點內有同時約束多個介面的需求（錯誤處理、安全、啟動檢查、migration、交易原子性等）時，另設一個 `<端點>共通介面` 承接，排在該端點所有介面之前。
- 端點沒有跨功能需求時不設共通介面；只約束單一介面的需求歸入該介面。

## Good Example
- 後端的錯誤碼、本機連線限制與啟動檢查同時約束所有 API，集中在共通介面；檔案儲存的空間檢查只關係原檔寫入，歸入原檔儲存介面，不放進共通介面。

```
6. `後端共通介面`
    - 主要介面：錯誤碼與 HTTP 狀態對應、本機連線限制、啟動時檢查資料庫連線與儲存目錄
16. `原檔儲存介面`
    - 主要介面：原檔目錄、寫入前空間檢查
```

## Bad Example
- 本機連線限制約束所有 API，卻分散寫進每個 API 介面，責任重複且容易漏掉其中一個。

```
7. `相簿 API 介面`
    - 主要介面：相簿建立、改名、刪除、本機連線限制
8. `照片 API 介面`
    - 主要介面：多檔照片上傳、本機連線限制
```

# Rule 3 - 需求原文依據的寫法 [MUST]
- 優先引用 spec.md Input 的使用者原話，以「」包住。
- 使用者原話未涵蓋該介面時，改寫「需求要求……」概述 spec.md 中的要求，不偽造引號。
- 句末一律以「；對應 `FR-xxx`、`NFR-xxx` 與 `FR-yyy`。」列出全部對應條目編號。

## Good Example
- 原話涵蓋的介面引用原話；原話沒提到匯出，改用「需求要求」，兩者都以對應條目收尾。

```
- 需求原文依據：使用者描述要求「在每個相簿中，照片會以平鋪式的介面進行預覽」；對應 `FR-020`、`FR-020a`、`FR-021` 與 `FR-028`。
- 需求原文依據：需求要求使用者能將照片原檔與相簿結構匯出作為備份；對應 `FR-025` 與 `FR-032`。
```

## Bad Example
- 第一行把 spec 條文當成使用者原話加上引號；第二行沒有列出對應條目，讀者無法回查。

```
- 需求原文依據：使用者描述要求「系統 MUST 提供匯出全部操作」；對應 `FR-025`。
- 需求原文依據：使用者描述要求「相簿要按日期分組」。
```

# Rule 4 - 每條約束介面的 FR / NFR 至少歸屬一個介面 [MUST]
- 盤點完成後，spec.md 中約束某個介面的每條 FR 與 NFR 編號，都必須出現在至少一個介面的需求原文依據中；連續編號可寫成 `FR-016` ~ `FR-016c`。
- 只約束開發流程、不屬於任何介面的條目（測試覆蓋率、測試決定性、效能量測進 CI、遙測政策等）不列入。
- 其餘找不到歸屬的條目，代表漏了介面或漏了共通介面，回頭補上，不得略過。

## Good Example
- NFR-027 約束所有 API，原本無處歸屬，補設後端共通介面承接。

```
6. `後端共通介面`
    - 需求原文依據：需求要求後端預設只接受本機連線……；對應 `NFR-004a`、`NFR-027` 與 `NFR-028`。
```

## Bad Example
- spec.md 有 NFR-030（migration 管理），但沒有任何介面列出它，資料庫的 migration 分析會被遺漏。

```
12. `albums 資料表介面` ……對應 `FR-003`、`FR-010`
13. `photos 資料表介面` ……對應 `FR-006`、`FR-007`
（全文找不到 `NFR-030`）
```

# Rule 5 - 主要介面只列功能範圍 [MUST]
- 主要介面只列該介面涵蓋哪些功能或責任，以名詞片語頓號串列。
- 不寫分析結果：API 路徑與欄位、schema 欄位與型別、技術選型、套件名稱都留給後續委派的分析 skill。

## Good Example
- 只說明介面負責哪些事，沒有決定任何細節。

```
- 主要介面：照片歸屬相簿、拍攝日期與日期來源、檔案路徑、內容雜湊
```

## Bad Example
- 已經寫出欄位型別與技術選型，等於提前做了系統分析。

```
- 主要介面：`photos(id BIGINT PK, album_id BIGINT FK, taken_at VARCHAR(19), sha256 CHAR(64))`，以 Prisma 管理
```
