# Rule 1 - 每批工作區三項通過，待定失敗不計 [MUST]
- 一批任務完成的判準：該批所屬工作區的型別檢查、lint 與單元 / 整合測試通過，先前已綠的測試仍綠。
- 只因「同 Phase 內尚未執行的任務的檔案還不存在」而失敗的測試或型別錯誤視為待定，不計失敗；到該 Phase 末的 Checkpoint 必須清零。
- `/tdd 紅燈` 任務新寫的測試失敗，在同一案例卡的 `/tdd 綠燈` 任務完成前視為待定；案例卡為防回歸（預期不先紅）或旅程（預期不先紅）時例外，其紅燈測試必須通過。
- 帶 `/tdd <步驟>` 標記的任務，除上述一鍵驗證外，另執行該任務案例卡的測試（含端對端與量測）作為該任務的驗證；其餘端對端、負載與效能量測不在每批執行，留給 Checkpoint 與驗證 Phase 的任務。

## Good Example
- 前端共通單元測試裡 connection.test.ts 找不到 connection.ts，而 connection.ts 是同 Phase 後面的序列任務，判為待定；其餘測試與型別檢查、lint 都通過，這批算完成。
- TDD Slice 卡的紅燈任務只有自己新寫的端對端測試失敗，判為待定；綠燈任務完成後該測試轉綠。

```
批次：T020 [P] 單元測試、T021–T026 [P] 元件與工具
結果：tsc 1 個錯誤（connection.test.ts 匯入不存在的 ../src/realtime/connection.ts）→ 待定（T028 尚未執行）
      lint 通過；vitest 23 通過、1 失敗（同上）→ 待定
判定：完成；Phase 2 Checkpoint 前 T028 做完後必須全綠

批次：T003 [US1] `/tdd 紅燈` SL-001（TDD Slice）
結果：typecheck、lint、pytest 全過；npx playwright test chat.spec.ts -g SL-001 → 1 failed → 待定（T004 綠燈尚未執行）
判定：完成
批次：T004 [US1] `/tdd 綠燈` SL-001
結果：typecheck、lint、pytest 全過；npx playwright test chat.spec.ts -g SL-001 → 1 passed
判定：完成
```

## Bad Example
- 把與尚未執行的任務無關的失敗也當待定，直接往下走。
- 防回歸卡的紅燈測試失敗也當成待定，前面實作的缺口被帶進下一批。

```
批次：T021–T026
結果：vitest 1 失敗（datetime.test.ts 期望 2024/03/05 14:07，實得 2024-03-05T06:07Z）
判定：待定 → 繼續下一批     // datetime.ts 就是這批的 T023，是真失敗

批次：T009 [US1] `/tdd 紅燈` SL-005（防回歸（預期不先紅））
結果：pytest -k sl_005 → 1 failed
判定：待定 → 繼續下一批     // 防回歸卡的紅燈必須通過，是真失敗
```

# Rule 2 - 不改測試與輸入文件求通過 [MUST]
- 驗證失敗時不得修改測試的期望值、刪除斷言或跳過測試讓它通過；也不得修改 specs/ 底下的任何輸入文件。
- 測試或文件與 Must Read 部位矛盾時，依 Must Read 實作並把矛盾列入回報，不自行裁決改哪一邊。

## Good Example
- 測試期望值與 research.md 的四捨五入規則不同，依 research.md 實作，測試照留並回報矛盾。

```
失敗：record-service.test.ts 期望勝率 33.33，research.md R12 定為一位小數 33.3
處理：依 R12 實作回傳 33.3；測試不改；回報「R12 與 T059 測試的小數位數不一致，請修正上游」
```

## Bad Example
- 為了讓測試過把期望值改掉，或在測試上加 skip。

```
失敗：同上
處理：把測試的 33.33 改成 33.3            // 改了測試
      或 it.skip("US2-AS01 勝率顯示")      // 跳過測試
```

# Rule 3 - 機械不一致照契約做並回報，設計衝突依優先序裁決 [MUST]
- 路徑、命名這類機械不一致，以 plan.md 的樹與 analysis/ 的契約為準照常實作，差異列入回報。
- 會改變做什麼的設計衝突，依固定優先序自行裁決：`analysis/` 契約 > `research.md` > `techstack.md` > `spec.md` > `plan.md`；裁決結果與衝突原文列入回報，不向使用者提問。

## Good Example
- research.md 的表名與 dbml 不同屬機械不一致，照 dbml；frontend.md 與 spec.md 對空態文案不同屬設計衝突，照優先序取 frontend.md，兩者都回報。

```
機械：research.md R5 寫 purchase_orders，schema.dbml 是 Table orders → 用 orders，回報 R5
設計：frontend.md 空態文案「購物車是空的」，spec.md FR-012 寫「尚無商品」→ analysis/ 優先，用「購物車是空的」，回報 FR-012 與 frontend.md 的差異
```

## Bad Example
- 碰到設計衝突停下來問使用者，或兩邊各做一半。

```
設計：同上 → 「請問文案要用哪一個？」       // 停下來問
      或 清單頁用「購物車是空的」、側欄用「尚無商品」   // 兩邊各一半
```

# Rule 4 - 只寫任務列出的路徑，repo 衛生檔例外 [SHOULD]
- 程式只寫在任務列出的路徑；Setup 任務建立的 ignore 檔與環境變數範本是固定例外。
- 其他必要的新增或修改（共用型別、輔助函式、既有檔的小改）列入回報的「任務路徑之外新增或修改的檔案」。

## Good Example
- 任務只列 cart-service.ts，實作時需要在既有 errors.ts 加一個錯誤碼，照加並回報。

```
任務路徑：backend/src/services/cart-service.ts
額外修改：backend/src/lib/errors.ts（新增 CART_ITEM_OUT_OF_STOCK）→ 列入回報
```

## Bad Example
- 額外新增了一個 utils 檔卻沒回報，plan.md 的樹與實際檔案從此對不上。

```
任務路徑：backend/src/services/cart-service.ts
額外新增：backend/src/services/cart-utils.ts → 未回報
```

# Rule 5 - Setup 任務建立一鍵驗證指令與 repo 衛生 [MUST]
- Setup 任務完成時，從程式碼根目錄能以單一指令分別執行 lint、型別檢查與測試，後續每批任務都用這些指令驗證。
- 依 techstack.md 列的工具建立或補齊 ignore 檔：git → `.gitignore`、Prettier → `.prettierignore`、ESLint flat config → `ignores`；已存在只補缺的關鍵 pattern。pattern 只列該技術堆疊與通用的，不套其他語言。
- 密鑰與連線字串只寫範本檔（如 `.env.example`），不寫實值；相依目錄、建置輸出、覆蓋率與測試結果不入庫。

## Good Example
- 根目錄一鍵指令齊全，Node 堆疊的 ignore 檔只列相關 pattern，密鑰只有範本。

```
package.json scripts: lint / typecheck / test
.gitignore:       node_modules/  dist/  coverage/  test-results/  *.log  .env*  .DS_Store
.prettierignore:  node_modules/  dist/  coverage/  package-lock.json
eslint.config.js: ignores: ["node_modules/", "dist/", "coverage/"]
backend/.env.example: DATABASE_URL=mysql://user:pass@localhost:3306/app
```

## Bad Example
- 沒有一鍵指令，每批驗證要自己拼指令；ignore 檔貼了 Python、Java 的 pattern；.env 寫了真實密碼。

```
package.json scripts: （無）
.gitignore: __pycache__/  target/  *.class  node_modules/
backend/.env: DATABASE_URL=mysql://root:MyRealPassword@...
```

# Rule 6 - 回報固定包含五項 [MUST]
- 子代理完成任務的回報固定包含：執行的驗證指令與結果、任務路徑之外新增或修改的檔案、文件未規定而自行決定的事項、發現的文件不一致與裁決、Why 驗收結果。
- 沒有內容的項目寫「無」，不省略。

## Good Example
- 五項齊全，沒有內容的寫「無」。

```
驗證：npm run typecheck ✔、npm run lint ✔、npm test -w backend ✔（31 通過）
額外檔案：backend/src/lib/errors.ts（新增 CART_ITEM_OUT_OF_STOCK）
自行決定：購物車逾時清理間隔文件未定，取 60 秒
文件不一致：無
Why 驗收：累加用 ON DUPLICATE KEY UPDATE，通過
```

## Bad Example
- 只回一句「完成」，協調者無從驗證也無從彙整當責紀錄。

```
T031 完成，測試都過。
```

# Rule 7 - 測試與程式都標出對應的案例卡編號 [MUST]
- `/tdd 紅燈` 任務新寫的測試，測試名稱以案例卡編號開頭（如 `SL-012 ...`、`test_sl_012_...`），讓 test-plan.md 的每張卡都能在測試檔中搜尋到。
- `/tdd 綠燈` 任務完成時，在該卡行為所在的每個程式檔（含任務路徑之外為該卡新增或修改的檔案）檔首註解列出案例卡編號；檔首已有清單就把新編號依序補進同一段，不另起一段。
- 防回歸（預期不先紅）與旅程（預期不先紅）卡沒有綠燈任務，由紅燈任務在受測行為所在的程式檔檔首另列一行「回歸 / 旅程案例」編號。
- 註解格式依檔案類型使用該語言的註解語法（`//`、`--`、`/* */`、`<!-- -->`），格式化與 lint 仍須通過；設定檔、測試設定（如覆蓋率門檻）同樣適用。

## Good Example
- 綠燈改了 service 與既有 repository，兩個檔案的檔首清單都補上 SL-012；防回歸卡 SL-013 在 service 檔首另列一行。

```
// Test-plan cases (specs/001-shop/test-plan.md) whose behavior this file implements:
//   SL-004, SL-012
// Regression/journey cases (no green task) that exercise this file: SL-013
export class CartService { ... }

測試：it('SL-012 adding an out-of-stock item is rejected', ...)
```

## Bad Example
- 只在測試名稱寫編號，程式檔沒有任何標記；或任務路徑之外改的檔案漏標，使用者無法從案例卡找到實作。

```
// cart-service.ts — 檔首沒有任何 SL 編號
// errors.ts — 為 SL-012 新增 CART_ITEM_OUT_OF_STOCK，未標 SL-012
測試：it('rejects out-of-stock items', ...)        // 名稱沒有案例卡編號
```
