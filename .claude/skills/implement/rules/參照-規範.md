# Rule 1 - Must Read 讀到部位，Optional 只在不夠用時補讀 [MUST]
- Must Read 的每個部位都要實際讀到該識別碼所在的段落、章節、路徑或欄位，讀了同檔其他位置不算完成參照。
- Optional 只在 Must Read 不足以決定實作時才讀；Must Read 已能決定的不讀。

## Good Example
- 任務的 Must Read 指到 R8 的「注意」子段與 dbml 的兩個欄位，執行者逐一定位到這些部位；Optional 的 plan.md 因 Must Read 已足夠而未讀。

```
Must Read:
  research.md -> R8. 庫存扣減與並行控制 › 注意   → 讀 ## R8 底下的 **注意** 段
  analysis/schema.dbml -> Table cart_items.quantity  → 讀 Table cart_items 的 quantity 欄與其 note
Optional:
  plan.md -> Source Code (repository root)          → 未讀（Must Read 已足夠）
```

## Bad Example
- 只讀了 research.md 開頭的摘要表就當作讀過 R8，並把 Optional 整份 plan.md 一次讀進來。

```
Must Read:
  research.md -> R8. 庫存扣減與並行控制 › 注意   → 讀了檔首的決策摘要表，沒讀 R8
Optional:
  plan.md -> Source Code (repository root)          → 整份 plan.md 讀完
```

# Rule 2 - 文件中的具體值照抄，不自創 [MUST]
- 環境變數名、預設值、錯誤碼、事件名、欄位名、套件版本、門檻數字、文案等文件已寫明的值，一律照文件使用。
- 文件沒寫的值才由執行者決定，並列入回報的「自行決定的事項」。

## Good Example
- 錯誤碼與套件版本都取自文件原文。

```
openapi.yaml schemas.Error 的 code 列舉：CART_ITEM_OUT_OF_STOCK
→ 程式回傳 { code: "CART_ITEM_OUT_OF_STOCK" }
techstack.md Runtime Dependencies：fastify 5.12.7
→ package.json "fastify": "5.12.7"
```

## Bad Example
- 錯誤碼自創同義名、版本改用範圍，前端對照表與鎖定版本都對不上。

```
→ 程式回傳 { code: "OUT_OF_STOCK" }
→ package.json "fastify": "^5"
```

# Rule 3 - 先讀要 import 或修改的既有程式檔 [MUST]
- 任務要 import、呼叫或修改的既有程式檔，實作前先讀其匯出介面與既有慣例，再寫程式。
- 判準：實作中出現的任何既有模組名稱，都要能對到一次實際讀取。

## Good Example
- 購物車服務要用資料庫連線與時鐘，先讀兩個檔的匯出，再依其簽章撰寫。

```
任務：實作購物車服務於 backend/src/services/cart-service.ts
先讀：backend/src/db/client.ts（匯出 withTransaction(fn)）
      backend/src/lib/clock.ts（匯出 Clock 介面與 systemClock）
再寫：export function createCartService(db, clock: Clock) { ... withTransaction(...) }
```

## Bad Example
- 沒讀既有檔，憑印象假設連線模組匯出 `query`，型別檢查才發現不存在。

```
任務：實作購物車服務於 backend/src/services/cart-service.ts
未讀：backend/src/db/client.ts
寫成：import { query } from "../db/client.ts"   // client.ts 沒有 query
```

# Rule 4 - Why 是完成前的驗收項 [MUST]
- 任務回報完成前，回讀該任務的 Why，確認它指出的錯誤在實作中沒有發生。
- Why 指出的錯誤若在實作中出現，任務未完成，回到 Must Read 的部位修正。

## Good Example
- Why 說「照直覺寫會在並行下少算」，完成前確認累加用的是唯一鍵衝突時更新。

```
Why: 同一訪客同時加入同一商品時數量要正確累加，dbml 已定下用唯一鍵衝突時更新而非先讀再寫，照直覺寫會在並行下少算。
驗收：cart-service.ts 的加入用 INSERT ... ON DUPLICATE KEY UPDATE quantity = quantity + VALUES(quantity) → 通過
```

## Bad Example
- 測試綠了就回報完成，沒回讀 Why；實作用的是先 SELECT 再 UPDATE，正是 Why 警告的寫法。

```
Why: …照直覺寫會在並行下少算。
驗收：未回讀 Why；cart-service.ts 先 SELECT quantity 再 UPDATE → 回報完成
```
