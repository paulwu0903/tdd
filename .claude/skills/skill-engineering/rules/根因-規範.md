# Rule 1 - 預期寫成可觀察的產出 [MUST]
- 預期要寫成「給定這個輸入，產出應該是什麼、不該有什麼」，讓任何人拿到同一份輸入都能判斷產出是否符合。
- 「更好」「更準」「更完整」這類形容不算預期。

## Good Example
- 下方 Bad Example 的改良版：指明輸入、產出的對應關係與不該出現的東西。

```
輸入：git log 的 12 筆 commit
預期：changelog 每一條都能對回其中一筆 commit，不出現 log 以外的項目
```

## Bad Example
- 只有形容詞，無法判斷任何一份產出是否符合。

```
預期：changelog 要更準確
```

# Rule 2 - 根因定位到部件 [MUST]
- 根因寫成「哪個 skill 的哪個部件（SOP 步驟、rule、template、script、description、上下游介面）缺什麼或多什麼」。
- 定位不到部件的描述不是根因，不得進入編排。

## Good Example
- 下方 Bad Example 的改良版：指到 skill、步驟與缺的參數。

```
根因：changelog/SKILL.md Phase 1 第 1 步只讀最近 10 筆 commit，缺 --since 參數，本次需要的 12 筆少讀 2 筆
```

## Bad Example
- 兩句都指不到任何部件，無法據此決定改什麼。

```
根因：changelog skill 寫得不夠好
根因：模型產生幻覺
```

# Rule 3 - 以首次偏離點為根因 [MUST]
- 以實際輸入從第一步走到最後一步，逐步記錄該步拿到什麼、做出什麼；第一個與預期不符的步驟是根因所在，之後的偏離視為承襲。
- 根因要能解釋「照現有部件走，必然得到現況」；解釋不了的只是猜測。

## Good Example
- 整條鏈都走過，第一個偏離在第 1 步，第 2 步的編造是承襲，根因只定一個。

```
| 步驟          | 該步輸入       | 實際產出              | 偏離     |
| Phase 1 第 1 步 | git log       | 10 筆 commit（預期 12） | 首次偏離 |
| Phase 1 第 2 步 | 10 筆 commit  | 12 條 changelog，2 條無對應 | 承襲上游 |
根因：第 1 步少讀 2 筆，第 2 步只能補寫 2 條，必然出現 log 以外的項目
```

## Bad Example
- 只看最後一步，沒有往前走，把承襲的偏離當成根因。

```
| 步驟          | 該步輸入       | 實際產出              | 偏離     |
| Phase 1 第 2 步 | 10 筆 commit  | 12 條 changelog，2 條無對應 | 首次偏離 |
根因：第 2 步編造了 2 條
```

# Rule 4 - 根因不是症狀的重述 [MUST]
- 「產出裡有 X」「產出少了 Y」是症狀。
- 若根因只能寫成「缺一條禁止 X 的規則」，先檢查上游步驟是否缺輸入或缺判斷依據；只有確認上游無缺，根因才可定為「判斷缺規則」。

## Good Example
- 候選根因是缺禁止規則，回頭檢查上游後發現是步驟缺輸入，根因改定在第 1 步。

```
症狀：changelog 出現 log 以外的項目
候選：rules/Changelog-規範.md 缺「不得編造」 → 檢查上游
上游：Phase 1 第 1 步缺 --since，少讀 2 筆
根因：步驟缺輸入（Phase 1 第 1 步）
```

## Bad Example
- 把症狀改寫成禁止句就當根因，沒有檢查上游；加了規則後第 1 步照樣少讀，症狀會換個形式再出現。

```
症狀：changelog 出現 log 以外的項目
根因：rules/Changelog-規範.md 缺「不得包含 git log 以外的項目」
```
