# Rule 1 - 任務句型以動作開頭、以路徑收尾 [MUST]
- 任務描述以動作開頭（建立、實作、撰寫、串接、掛載等），接做的內容，以「於 `路徑`」收尾。
- 多個檔案以「、」分隔，每個路徑各自用反引號包住。
- 沒有產出檔的執行類任務（例如全量驗證）不加「於 `路徑`」。

## Good Example
- 環境任務動作在前、內容在中、以「於 `路徑`」收尾；綠燈任務的兩個路徑各自反引號並以「、」分隔。

```
- [ ] T001 [P] `環境` 加入負載量測的依賴與 pytest marker 於 `backend/pyproject.toml`
- [ ] T012 [US1] `/tdd 綠燈` 實作 SL-007 的行為於 `backend/app/chat_rules.py`、`backend/app/chat.py`
```

## Bad Example
- 沒有動作、路徑放在句首且多個路徑擠在同一組反引號裡。

```
- [ ] T001 [P] `環境` `backend/pyproject.toml, frontend/playwright.config.ts` 的量測設定
```

# Rule 2 - 路徑以 plan.md 的 Source Code 樹為準 [MUST]
- 任務路徑取自 plan.md 的 Source Code 樹，不採用 research.md 或其他文件裡的路徑寫法。
- plan.md 未列的檔案仍可列任務，路徑放在 plan.md 樹中對應的目錄下。

## Good Example
- 負載量測檔照用 plan.md 樹的 `backend/tests/load/`；plan.md 未列的 Playwright 設定檔放在樹中的 `frontend/` 下。

```
- [ ] T057 `/tdd 紅燈` 撰寫 SL-035 的測試於 `backend/tests/load/test_chat_load.py`
- [ ] T002 [P] `環境` 新增 NFR 量測的 Playwright 專案與畫面寬度設定於 `frontend/playwright.config.ts`
```

## Bad Example
- 任務照抄其他文件的 `packages/server` 路徑，與 plan.md 的樹不一致。

```
- [ ] T057 `/tdd 紅燈` 撰寫 SL-035 的測試於 `packages/server/tests/load/test_chat_load.py`
```

# Rule 3 - 輸入文件不一致時回報上游，不在 tasks.md 補註 [MUST]
- 路徑、命名這類機械不一致（例如 research.md 的路徑與 plan.md 的樹不同、research.md 與 dbml 的表名不同）以 plan.md 的樹與 analysis/ 的契約為準照常展開，完成時向使用者回報需在哪份上游文件修正。
- 會改變做什麼的設計衝突（例如字型載入方式、主題範圍）不自行裁決，停下來向使用者提出。
- tasks.md 不設 Notes、Dependencies 之類的段落來記錄裁決；任務列、[P] 與 Must Read 已表達全部執行所需的資訊。

## Good Example
- 展開照 dbml 的表名，回報時指出 research.md 要改。

```
任務：- [ ] T059 [US2] 實作結帳交易…於 `backend/src/db/checkout.ts`（Must Read 引 `Table orders`）
回報：research.md R5 的表名 `purchase_orders` 與 analysis/schema.dbml 的 `orders` 不一致，tasks 以 dbml 為準，請修正 R5
```

## Bad Example
- 把不一致寫成 tasks.md 的 Notes 自行消化，上游文件永遠不會被修。

```
## Notes
- 表名以 dbml 的 `orders` 為準，research.md R5 的 `purchase_orders` 即此表
```

# Rule 4 - 步驟標記與四種句型 [MUST]
- 任務描述以步驟標記開頭，標記放在 [P] 與 [US] 之後，句型依步驟固定：

| 步驟 | 句型 |
|---|---|
| 環境 | `` `環境` <動作與內容>於 `路徑` `` |
| 紅燈 | `` `/tdd 紅燈` 撰寫 SL-nnn 的測試於 `路徑` `` |
| 綠燈 | `` `/tdd 綠燈` 實作 SL-nnn 的行為於 `路徑` `` |
| 重構 | `` `/tdd 重構` 整理 User Story n 的程式碼於 `路徑` ``，全域 NFR Phase 寫 `` `/tdd 重構` 整理全域 NFR 的程式碼於 `路徑` `` |

## Good Example
- 四種步驟各用自己的標記與句型。

```
- [ ] T001 [P] `環境` 加入負載量測的依賴與 pytest marker 於 `backend/pyproject.toml`
- [ ] T011 [US1] `/tdd 紅燈` 撰寫 SL-007 的測試於 `backend/tests/test_chat.py`
- [ ] T012 [US1] `/tdd 綠燈` 實作 SL-007 的行為於 `backend/app/chat_rules.py`、`backend/app/chat.py`
- [ ] T063 `/tdd 重構` 整理全域 NFR 的程式碼於 `backend/app/chat.py`、`backend/app/models.py`
```

## Bad Example
- 沒有步驟標記，執行者無法判斷要走 /tdd 的哪一步。

```
- [ ] T011 [US1] 撰寫 SL-007 的測試於 `backend/tests/test_chat.py`
```

# Rule 5 - 任務句不重述案例卡 [MUST]
- 紅燈與綠燈的任務句只寫步驟標記、卡片 ID 與路徑，不寫卡片標題、測試意圖、oracle 或錯誤碼；卡片內容由 Must Read 指回 test-plan.md。

## Good Example
- 只有卡片 ID，內容留在 test-plan.md。

```
- [ ] T011 [US1] `/tdd 紅燈` 撰寫 SL-007 的測試於 `backend/tests/test_chat.py`
```

## Bad Example
- 把卡片標題與預期結果抄進任務句，test-plan.md 修改後兩邊就不一致。

```
- [ ] T011 [US1] `/tdd 紅燈` 撰寫 SL-007 空白與過長的訊息被拒絕並回傳錯誤原因的測試於 `backend/tests/test_chat.py`
```

# Rule 6 - [P] 只用於環境任務 [MUST]
- 只有 `環境` 任務可標 [P]，且須與其他標 [P] 的任務寫不同檔、不依賴彼此的產出。
- 紅燈、綠燈與重構任務依 /tdd 的步驟順序執行，一律不標 [P]。

## Good Example
- 兩個環境任務各改一個設定檔，彼此無依賴，都標 [P]。

```
- [ ] T001 [P] `環境` 加入負載量測的依賴與 pytest marker 於 `backend/pyproject.toml`
- [ ] T002 [P] `環境` 新增 NFR 量測的 Playwright 專案與畫面寬度設定於 `frontend/playwright.config.ts`
```

## Bad Example
- 紅燈任務標了 [P]，它與前一張卡寫同一個測試檔，平行執行會互相覆寫。

```
- [ ] T005 [P] [US1] `/tdd 紅燈` 撰寫 SL-002 的測試於 `frontend/e2e/chat.spec.ts`
```
