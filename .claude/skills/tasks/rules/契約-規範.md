# Rule 1 - 部位只寫識別碼 [MUST]
- 契約行的每個部位只寫該文件裡可以直接定位的識別碼，不附括號說明、不列套件名與版本。
- 各文件的識別碼寫法：

| 文件 | 識別碼寫法 |
|---|---|
| `spec.md` | `使用者故事 n`、`FR-nnn`、`NFR-nnn`、`SC-nnn`、`使用者故事 n › Acceptance Scenarios a, b` |
| `test-plan.md` | 案例卡 `SL-nnn`、Fixture `<seam>-FX-<狀態>`、段落 `User Story n`、`全域 NFR`、`跨故事旅程` |
| `research.md` | `R<n>. 標題`，需要時加 ` › 子段`；子段取該章節內的粗體標籤（Decision、Rationale、注意）或 bullet 開頭詞 |
| `techstack.md`、`plan.md` | 章節名，需要時加 ` › 子項` |
| `analysis/openapi.yaml` | 路徑（如 `/api/cart`）、`schemas.Name` |
| `analysis/asyncapi.yaml` | `channels.x`、`operations.x`、`messages.x`、`schemas.x` |
| `analysis/schema.dbml` | `Table 表.欄位`、`Table 表`、`TableGroup 名 › 子段` |
| `analysis/frontend.md` | `章節 › 子項` |
| `analysis/prototype/*` | 檔名，需要時加 `?state=` |

## Good Example
- 每個部位都是能在文件中直接找到的識別碼。

```
    - `spec.md` -> `使用者故事 1`, `FR-004`, `FR-005`, `NFR-003`
    - `analysis/schema.dbml` -> `Table cart_items.quantity`, `TableGroup 資料庫共通介面 › 購物車`
    - `research.md` -> `R8. 庫存扣減與並行控制 › 購物車`
```

## Bad Example
- 部位後面附了括號說明，techstack 的部位變成套件名與版本清單。

```
    - `research.md` -> `R8. 庫存扣減與並行控制`（加入購物車只檢查不扣庫存、累加用 ON CONFLICT）
    - `techstack.md` -> `Runtime Dependencies`（fastify 5.12.7、zod 4.6.7、pg 8.13.0）
```

# Rule 2 - spec.md 先故事段再編號 [SHOULD]
- 引用 spec.md 時，先列 `使用者故事 n`，再列該故事底下的 FR / NFR / Scenario 編號，讓執行者先讀敘述再讀規則。

## Good Example
- 故事段在前，編號在後。

```
    - `spec.md` -> `使用者故事 2`, `FR-011`, `FR-012`, `FR-013`, `NFR-005`
```

## Bad Example
- 只列編號，執行者不知道這些需求屬於哪個故事、脈絡是什麼。

```
    - `spec.md` -> `FR-011`, `FR-012`, `FR-013`, `NFR-005`
```

# Rule 3 - 任務只碰特定欄位時 dbml 寫到欄位 [SHOULD]
- 任務只讀寫資料表的部分欄位時，部位寫 `Table 表.欄位`，每個碰到的欄位各一個。
- 建立整張表或碰到全部欄位的任務才寫 `Table 表`。

## Good Example
- 結帳交易只碰庫存、冪等鍵、狀態與單價快照四個欄位，逐欄列出。

```
    - `analysis/schema.dbml` -> `Table products.stock`, `Table orders.idempotency_key`, `Table orders.status`, `Table order_items.unit_price_cents`
```

## Bad Example
- 同一個結帳交易任務只寫整張表，執行者得自己猜要看哪些欄位。

```
    - `analysis/schema.dbml` -> `Table products`, `Table orders`, `Table order_items`
```

# Rule 4 - Optional 無內容時寫「無」 [MUST]
- Optional 沒有要列的部位時，底下寫一行「無」，不省略 Optional 段。

## Good Example
- Optional 段保留，內容為「無」。

```
  - Must Read:
    - `research.md` -> `依賴授權`
  - Optional:
    - 無
  - Why: 授權表已列出遞移依賴中非 MIT 的套件，腳本輸出須涵蓋各自的授權檔。
```

## Bad Example
- Optional 段整個省略，check_tasks.py 會判為缺段。

```
  - Must Read:
    - `research.md` -> `依賴授權`
  - Why: 授權表已列出遞移依賴中非 MIT 的套件，腳本輸出須涵蓋各自的授權檔。
```

# Rule 5 - Why 一句話說明不讀會錯在哪 [MUST]
- Why 只寫一句話，內容是不讀 Must Read 的部位時會在哪個決策或行為上做錯。
- 不重述部位清單、不重述任務內容。
- 不含程式識別碼（反引號）；要指到的識別碼放在 Must Read 的部位，Why 只用需求與文件的語言。

## Good Example
- 一句話，直接點出漏讀的後果，沒有任何程式識別碼。

```
  - Why: 同一訪客同時加入同一商品時數量要正確累加，dbml 已定下用唯一鍵衝突時更新而非先讀再寫，照直覺寫會在並行下少算。
```

## Bad Example
- 把實作細節與當場發明的函式名寫進 Why，這些是實作時才會決定的東西。

```
  - Why: `addItem` 要用 `INSERT ... ON CONFLICT DO UPDATE` 累加 `quantity`，再呼叫 `recalculateTotal` 回傳新購物車。
```

# Rule 6 - 契約行的文件限 Input Documents [MUST]
- Must Read 與 Optional 指向的文件只能是檔首 Input Documents 列出的輸入文件。
- 任務會產生的檔（程式、設定、種子資料）在規劃時還不存在，不得作為契約的文件。

## Good Example
- Optional 指向輸入文件 frontend.md 的假資料段。

```
  - Optional:
    - `analysis/frontend.md` -> `雛形 › 假資料`
```

## Bad Example
- Optional 指向 T007 才會產生的種子檔，規劃時讀不到。

```
  - Optional:
    - `backend/db/seed.sql`
```

# Rule 7 - 紅燈的 Must Read 含案例卡與用到的 Fixture [MUST]
- 紅燈任務的 Must Read 必含 `test-plan.md` -> 該卡的 `SL-nnn`，以及該卡前置狀態所依的 Fixture ID。
- 該紅燈要新增 helper 時，helper 依賴鏈上的 Fixture 一併列出。

## Good Example
- SL-002 只依雙人同房的 Fixture；SL-001 是第一張 UI 卡要建立 helper，依賴鏈上的 Fixture 全部列出。

```
- [ ] T005 [US1] `/tdd 紅燈` 撰寫 SL-002 的測試於 `frontend/e2e/chat.spec.ts`
  - Must Read:
    - `test-plan.md` -> `SL-002`, `UI-FX-TWO-IN-ROOM`
- [ ] T003 [US1] `/tdd 紅燈` 撰寫 SL-001 的測試於 `frontend/e2e/chat.spec.ts`、`frontend/e2e/support.ts`
  - Must Read:
    - `test-plan.md` -> `SL-001`, `UI-FX-SERVER`, `UI-FX-UNIQUE-CODE`, `UI-FX-GUEST`, `UI-FX-HOST-WAITING`, `UI-FX-TWO-IN-ROOM`
```

## Bad Example
- 只列案例卡，沒有 Fixture，執行者會自行建立前置狀態，與 test-plan.md 的就緒條件對不上。

```
- [ ] T005 [US1] `/tdd 紅燈` 撰寫 SL-002 的測試於 `frontend/e2e/chat.spec.ts`
  - Must Read:
    - `test-plan.md` -> `SL-002`
```

# Rule 8 - 綠燈的 Must Read 含案例卡 [MUST]
- 綠燈任務的 Must Read 必含 `test-plan.md` -> 該卡的 `SL-nnn`。

## Good Example
- 綠燈先指回案例卡，再列實作要遵守的契約。

```
- [ ] T012 [US1] `/tdd 綠燈` 實作 SL-007 的行為於 `backend/app/chat_rules.py`、`backend/app/chat.py`
  - Must Read:
    - `test-plan.md` -> `SL-007`
    - `research.md` -> `R3. 字元數計算`
```

## Bad Example
- 綠燈沒有指回案例卡，執行者不知道要讓哪一個測試通過。

```
- [ ] T012 [US1] `/tdd 綠燈` 實作 SL-007 的行為於 `backend/app/chat_rules.py`、`backend/app/chat.py`
  - Must Read:
    - `research.md` -> `R3. 字元數計算`
```
