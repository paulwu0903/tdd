# Rule 1 - tag 名稱與後端介面一字不差 [MUST]
- plan.md 中端點類型為 `後端端點` 的每個介面，都要在 openapi.yaml 的 `tags` 或 asyncapi.yaml 的 `info.tags` 有一個同名 tag，名稱一字不差。
- 每個 operation 只掛它所屬介面的 tag；tag 的 description 寫該介面的主要介面。
- 共通介面（如 `後端共通介面`）沒有自己的 API 時只宣告 tag，由 `securitySchemes`、`components.parameters`、`components.responses` 與 `Error` schema 承接，不為了掛 tag 而新增 API。

## Good Example
- plan.md 的介面名稱原樣成為 tag，即時事件介面的 tag 放在 asyncapi。

```
plan.md：3. `優惠券 API 介面`、5. `購物車通知 API 介面`
openapi.yaml：tags: - name: 優惠券 API 介面
asyncapi.yaml：info.tags: - name: 購物車通知 API 介面
```

## Bad Example
- tag 改寫成英文或縮寫，system-analysis 回檢時對不回 plan.md 的介面。

```
plan.md：3. `優惠券 API 介面`
openapi.yaml：tags: - name: Coupon
```

# Rule 2 - 行為規則寫在 description 的三段 [MUST]
- 每個 operation 的 description 依序寫「**業務規則**」條列、「**交易**」與「**對應需求**」三段，各段寫入時機如下：
    - 業務規則：有 schema 表達不了的規則時才寫
    - 交易：一次請求有兩項以上的寫入必須一起成功或一起失敗時才寫
    - 對應需求：每個 operation 都必寫
- asyncapi 的 operation 沒有交易段。
- 不用 `x-` 擴充欄位承載規則，因為 Swagger UI 的 `showExtensions` 預設為 false，`x-` 欄位不會顯示。

## Good Example
- 規則、交易與需求編號都在 description，Swagger 上直接看得到。

```yaml
description: |
  **業務規則**
  - 相同 `Idempotency-Key` 重送時回傳第一次的結果，不重複建立訂單

  **交易**：庫存檢查、庫存扣減、優惠券剩餘次數扣減、訂單建立與購物車清空在同一交易完成，任一失敗全部不生效

  **對應需求**：FR-008、FR-009、FR-010
```

## Bad Example
- 規則放在 `x-` 欄位，Swagger 預設畫面看不到；也沒有對應需求。

```yaml
description: 送出訂單
x-idempotent: true
x-transaction: [stock, orders, cart_items]
```

# Rule 3 - 每支 API 各自列出錯誤碼與發生情況 [MUST]
- 每個非 2xx 回應的 description 以「- `錯誤碼`：發生情況」逐條列出這支 API 在該狀態碼下可能回的全部錯誤碼。
- 多支 API 共用、發生情況相同的錯誤（如 session 缺失的 401）寫在 `components.responses`，各 API 以 `$ref` 引用。
- 錯誤本體一律用 `Error` schema，`code` 的 enum 收錄全部錯誤碼。

## Good Example
- 409 逐條列出錯誤碼與情況，共用的 401 以 `$ref` 引用。

```yaml
'401':
  $ref: '#/components/responses/SessionMissing'
'409':
  description: |
    - `CART_EMPTY`：購物車沒有任何商品
    - `OUT_OF_STOCK`：至少一項商品的數量超過目前庫存
```

## Bad Example
- 只寫狀態碼的通用說明，前端不知道會收到哪些錯誤碼；401 在每支 API 重複貼一份。

```yaml
'401':
  description: |
    - `SESSION_MISSING`：未帶 session
'409':
  description: Conflict
```

# Rule 4 - request 與 response 寫出完整 schema [MUST]
- 每個 request body、response body 與 parameter 都寫出完整的 schema：每個欄位的型別、必填、格式、範圍或 enum，以及欄位意義的 description。
- 重複出現的結構抽到 `components.schemas` 並以 `$ref` 引用。

## Good Example
- 欄位型別、必填、範圍與單位都寫明。

```yaml
CartItem:
  type: object
  required: [itemId, productId, quantity, unitPrice]
  properties:
    quantity: { type: integer, minimum: 1, maximum: 99 }
    unitPrice: { type: integer, minimum: 0, description: 新台幣，以元為單位的整數 }
```

## Bad Example
- 只寫 `type: object`，Swagger 上看不出欄位。

```yaml
CartItem:
  type: object
```

# Rule 5 - 有即時事件才產出 asyncapi，並以伺服器角度描述 [MUST]
- 後端介面需要伺服器主動推播或長連線雙向訊息時才產出 asyncapi.yaml；全部是請求與回應時不產出。
- operation 以伺服器角度寫 `action`：伺服器推播給前端為 `send`，伺服器接收前端訊息為 `receive`。
- payload 中與 HTTP API 相同意義的欄位，名稱與型別要和 openapi.yaml 的 schema 一致，並在 description 註明對應的 schema 欄位。

## Good Example
- 售完推播是伺服器送出，`itemId` 對回 openapi 的 `CartItem.itemId`。

```yaml
sendCartItemSoldOut:
  action: send
itemId:
  type: string
  description: 對應 openapi.yaml `CartItem.itemId`
```

## Bad Example
- 從前端角度把推播寫成 `receive`；欄位改名為 `cartItemId`，前端對不回購物車項目。

```yaml
receiveCartItemSoldOut:
  action: receive
cartItemId:
  type: string
```

# Rule 6 - 「交易」寫出參與的寫入與失敗處理 [SHOULD]
- 「交易」段寫出這支 API 在同一交易中完成的每一項寫入，以及任一步失敗時的處理，讓 data-plan 據此設計資料表的交易步驟與鎖定順序。

## Good Example
- 列出每一項寫入與失敗時全部不生效。

```
**交易**：庫存檢查、庫存扣減、優惠券剩餘次數扣減、訂單建立與購物車清空在同一交易完成，任一失敗全部不生效
```

## Bad Example
- 只寫「有交易」，data-plan 不知道哪些寫入要放在同一交易。

```
**交易**：有
```
