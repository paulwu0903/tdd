# Rule 1 - 只寫內建規則沒有的部分 [MUST]
- 對照目標產出物所屬 skill 的 `rules/` 與 `templates/`，已被內建規則涵蓋的內容不寫進憲法，只寫差異。

## Good Example
- api-plan 內建規則已要求寫出完整 schema，憲法只補上欄位命名。

```
內建：api-plan/契約設計-規範 Rule 4 request 與 response 寫出完整 schema
憲法：# Rule 2 - JSON 欄位名稱一律 lowerCamelCase [MUST]
```

## Bad Example
- 把內建規則重寫一次，徒增讀取量。

```
內建：api-plan/契約設計-規範 Rule 4 request 與 response 寫出完整 schema
憲法：# Rule 2 - 每個 request 與 response 都寫出完整 schema [MUST]
```

# Rule 2 - 與內建 Rule 衝突時，等級不低於被覆寫者 [MUST]
- 憲法條款與內建 Rule 衝突時以憲法為準；該條款的等級不得低於被它覆寫的內建 Rule。
- 回報時列出被覆寫的內建 Rule。

## Good Example
- 內建為 SHOULD，憲法提高為 MUST。

```
內建：specify/需求歸屬-規範 Rule 8 NFR 逐類掃描並標明類別 [SHOULD]
憲法：# Rule 1 - NFR 逐類掃描並標明類別，安全與資料完整性必有 [MUST]
```

## Bad Example
- 用較低等級覆寫內建 MUST，等於把錯誤格式放寬成可選。

```
內建：api-plan/契約設計-規範 Rule 3 每支 API 各自列出錯誤碼與發生情況 [MUST]
憲法：# Rule 4 - 錯誤包在 error 信封內 [SHOULD]
```

# Rule 3 - 只有程式驗證的 Rule 才寫「- 驗證：」 [MUST]
- 能由程式判定的 Rule，第一個 bullet 寫 `- 驗證：script checks/<名稱>.py`。
- implement 產出物中，由工作區既有 lint 判定的 Rule，第一個 bullet 寫 `- 驗證：lint`。
- 其餘 Rule 不寫驗證 bullet，由 skill 逐條自檢。

## Good Example
- 錯誤碼格式可由程式判定，寫驗證；錯誤本體不含內部細節需要判讀，不寫。

```
# Rule 5 - 錯誤碼為 UPPER_SNAKE_CASE [MUST]
- 驗證：script checks/error_code_format.py

# Rule 6 - 錯誤本體不含內部細節 [MUST]
- `message` 與錯誤本體不含 stack trace、SQL……
```

## Bad Example
- 需要判讀的 Rule 也加上驗證 bullet，卻沒有對應的程式。

```
# Rule 6 - 錯誤本體不含內部細節 [MUST]
- 驗證：review
```
