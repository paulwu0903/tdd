# Rule 1 - 依三層順序決定需求歸屬 [MUST]
- 每條 FR / NFR 依下表由上往下判斷，取第一個符合的位置。

| 順序 | 條件 | 位置 |
|---|---|---|
| 1 | 主要由某個 User Story 引入並驗證 | 該 User Story 底下 |
| 2 | 同等約束兩個以上 User Story，無法指定主要歸屬 | Global Requirements |
| 3 | 不約束任何 User Story 的使用者可觀察行為（部署、營運、隱私架構、開發流程） | System Constraints |

- 其他 User Story 需要用到時以編號引用，不重複列出。

## Good Example
- 三條需求各自落在第一個符合的位置。

```
FR-020 相簿頁面平鋪縮圖                     → US1（由 US1 驗收情境 5 引入並驗證）
NFR-001 主頁面與相簿頁面 2 秒內可互動        → Global（同等約束 US1、US2、US3）
NFR-028 後端以單一指令啟動並檢查資料庫連線   → System Constraints
```

## Bad Example
- 拖放排序雖然會用到 US3 的日期分組，但它是由 US4 引入並驗證，應該放在 US4。

```
- **FR-014**（適用：US3、US4）: 使用者 MUST 能以拖放調整同一日期分組內相簿的順序。
```

# Rule 2 - 「適用」列出每個受約束的 User Story [MUST]
- Global Requirements 的每一條，都要在「適用」逐一列出它約束的 User Story 編號。
- 不寫「全部」等概括字樣；新增 User Story 時要回頭檢查每一條是否需要補列。

## Good Example
- 六個 User Story 的介面都受錯誤訊息約束，逐一列出。

```
- **NFR-015**（適用：US1、US2、US3、US4、US5、US6）: 錯誤訊息 MUST NOT 曝露內部路徑、stack trace 或內部識別碼。
```

## Bad Example
- 寫「全部」，之後新增 US7 時沒人知道這條是否涵蓋它。

```
- **NFR-015**（適用：全部）: 錯誤訊息 MUST NOT 曝露內部路徑、stack trace 或內部識別碼。
```

# Rule 3 - 功能專屬內容拆成 FR / NFR，不另開章節 [MUST]
- 只有這次功能才需要的內容（例如前端介面的 loading / empty / error / success 狀態），拆成 FR 或 NFR 掛到對應的 User Story，不在 spec 中新增範本以外的章節或表格。

## Good Example
- 每個介面的四態各成一條 FR，掛在引入該介面的 User Story。

```
US1 - **FR-028**: 相簿頁面 MUST 實作四態：載入中顯示縮圖骨架格；無照片時顯示「此相簿尚無照片」…
US3 - **FR-030**: 主頁面 MUST 實作四態：載入中顯示分組骨架佔位且不閃爍；…
```

## Bad Example
- 另開一個範本沒有的章節放四態表格，需求脫離了 User Story。

```
### UX 四態定義
| 介面 | Loading | Empty | Error | Success |
```

# Rule 4 - 每個 User Story 至少一條需求 [MUST]
- 每個 User Story 的 FR 與 NFR 合計至少一條；只有 FR 或只有 NFR 都可以。
- 某一類沒有條目時，整個小節（含 `**Functional Requirements**:` 或 `**Non-Functional Requirements**:` 標題）省略，不為了湊數寫出空泛的需求。

## Good Example
- US4 的品質約束都已由 Global 需求（NFR-002、NFR-020）涵蓋，只寫 FR，NFR 小節整個省略。

```
**Functional Requirements**:

- **FR-014**: 使用者 MUST 能在主頁面以拖放方式調整同一日期分組內相簿的順序。
- **FR-015**: 使用者 MUST 能在主頁面將相簿拖放至另一日期分組；…
- **FR-018**: 所有手動排序結果 MUST 持久化；…

---
```

## Bad Example
- 為了讓 NFR 小節有內容，寫了一條無法驗證、也不屬於這個 User Story 的 NFR。

```
**Non-Functional Requirements**:

- **NFR-033**（效能）: 拖放排序操作應保持流暢。
```

# Rule 5 - Edge Case 的 MUST 由 FR / NFR 承接 [MUST]
- Edge Cases 帶出的每一個 MUST / MUST NOT，都要寫成 FR 或 NFR，歸屬依 Rule 1；已有需求涵蓋時直接引用，沒有就新增。
- Edge Case 本身只寫情境與「依 FR-xxx / NFR-xxx」的處理摘要，不自帶新的 MUST。

## Good Example
- 儲存空間不足的處理由 NFR-006 承接，Edge Case 只引用編號。

```
- 後端儲存空間不足：依 NFR-006 於寫入前檢查，拒絕該批中無法容納的檔案，已存資料不受影響。
- **NFR-006**（適用：US1、US2、US3、US4、US5）: … 後端儲存空間不足時 MUST 於寫入前明確告知並拒絕該批匯入，MUST NOT 造成已存資料損毀。
```

## Bad Example
- 三個 MUST 只寫在 Edge Case，沒有任何 FR / NFR 承接，也不會有對應的驗收與測試。

```
- 照片上傳途中網路中斷或後端停止：已完整寫入後端的照片 MUST 保留，未完成的檔案 MUST NOT 以半成品狀態出現在任何相簿；前端 MUST 列出未成功的檔案供使用者重新上傳。
```

# Rule 6 - 編號全域唯一且穩定 [MUST]
- FR、NFR 編號在整份 spec 唯一；新增需求取該類別下一個未使用的編號。
- 需求改變歸屬時不改號，同一個 User Story 內的編號不必連續。

## Good Example
- 四態需求後來才加入 US1，接續取 FR-028，不重排 US1 既有的編號。

```
US1：FR-004、FR-005、FR-007、FR-009、FR-020、FR-020a、FR-021、FR-024a、FR-028、FR-029
```

## Bad Example
- 為了讓 US1 連號而重排，所有引用 FR-020 的地方都會指錯。

```
US1：FR-001 ~ FR-010（原 FR-020 改為 FR-005）
```

# Rule 7 - FR / NFR 寫成可測試的 MUST 單句 [MUST]
- 每條以 MUST / MUST NOT 寫出一個可驗證的行為或門檻，帶具體數值或可觀察的結果。

## Good Example
- 有明確的上限與可觀察的結果。

```
- **FR-001**: 系統 MUST 允許使用者建立相簿，建立時 MUST 提供名稱；名稱 MUST NOT 為空白，長度上限 100 字元。
- **NFR-001**（適用：US1、US2、US3）: 含 1,000 張照片、50 個相簿的資料量下，主頁面 MUST 在 2 秒內可互動；…
```

## Bad Example
- 「快速」「好用」無法驗證。

```
- **NFR-001**（效能）: 系統應該要快速且好用。
```

# Rule 8 - NFR 逐類掃描並標明類別 [SHOULD]
- 推導每個 User Story 的 NFR 時，逐一檢查下列品質類別是否適用，適用者寫成 NFR 並在括號標明類別。
- 品質類別：效能、容量、可靠性與資料完整性、安全與隱私、可用性與無障礙、相容性、在地化、可維護性與可測試性、部署與營運。

## Good Example
- US1 的匯入流程逐類掃過，得到效能、容量、安全與隱私、相容性、部署與營運五類 NFR。

```
- **NFR-004**（效能）: 於同一台機器或區域網路（前端與後端之間頻寬 ≥ 1 Gbps）匯入 100 張、每張 10 MB 以內的照片，從開始上傳到全部可在「未分類」中預覽 MUST 在 60 秒內完成，…
- **NFR-007**（容量）: 單張照片檔案 MUST 支援至 50 MB；…
- **NFR-014**（安全與隱私）: 匯入檔案 MUST 經格式驗證；…
- **NFR-021**（相容性）: MUST 支援 FR-005 所列影像格式的正確解碼與縮圖產生，包含 HEIC；…
- **NFR-029**（部署與營運）: 後端 MUST 對上傳內容進行大小（NFR-007）、數量與格式（NFR-014）限制；…
```

## Bad Example
- 只想到效能，上傳檔案的格式驗證（安全）與 HEIC 解碼（相容性）都漏掉。

```
- **NFR-004**（效能）: 匯入 100 張照片 MUST 在 60 秒內完成。
```

# Rule 9 - 沒有項目的全域章節整章省略 [MUST]
- Global Requirements 或 System Constraints 沒有任何需求時，整個章節（含標題）省略，不留空標題或「無」。

## Good Example
- 所有需求都歸屬單一 User Story，spec 直接從 Edge Cases 接到 Key Entities。

```
### Edge Cases
…
## Key Entities
```

## Bad Example
- 留下空章節，讀者會以為漏寫。

```
## System Constraints（系統約束）

（無）
```
