# Rule 1 - 需求寫使用者可觀察的結果，不寫實作機制 [SHOULD]
- FR 描述使用者看得到、操作得到的行為與結果；達成方式留給技術設計。
- System Constraints 與「部署與營運」類 NFR 可描述營運面約束（例如啟動檢查、連線範圍），但仍只寫要達成的結果。

## Good Example
- 寫出使用者看到的結果，沒有規定怎麼載入。

```
- **FR-020**: 相簿頁面 MUST 以平鋪方式顯示相簿內所有照片的縮圖；捲動時 MUST NOT 出現長時間的空白格。
```

## Bad Example
- 寫的是載入步驟，使用者無從觀察，也替技術設計決定了做法。

```
- **FR-020**: 相簿頁面 MUST 先查詢縮圖清單，再依捲動位置逐一發出請求載入縮圖。
```

# Rule 2 - 不替技術設計選擇技術 [MUST]
- 使用者沒有指定的語言、框架、函式庫、資料庫、資料格式與介面形式，不得出現在 spec 中。
- 使用者指定的技術寫進 Assumptions 並標明使用者的決策來源；需求中只以元件角色（例如前端、後端）稱呼。

## Good Example
- 使用者指定的技術記在 Assumptions，並保留版本與套件給技術設計。

```
- **執行環境為瀏覽器 Web app + 自架後端**（使用者於 2026-10-23 修訂，取代原「純前端」決定）：… 使用者指定後端為 Node.js、資料庫為 MySQL；具體版本與套件留待技術設計階段決定。
```

## Bad Example
- 使用者沒有指定框架與影像函式庫，spec 卻替技術設計選好了。

```
- **FR-024b**: 後端 MUST 以 Express 提供 REST API，縮圖 MUST 以 Sharp 產生並存為 WebP。
```
