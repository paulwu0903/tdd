# Rule 1 - 字面歧義與會增減 User Story 的缺口才問 [MUST]
- 要問使用者的歧義只有兩種：
  - 功能描述寫到了，但字面有兩種以上讀法。
  - 功能描述沒寫到，但答案會新增或刪除一整個 User Story。
- 上述問題的答案再衍生出的細節，接著追問。
- 其餘歧義不問，依 Rule 3 處理。

## Good Example
- 前兩題是字面歧義，第三題的答案會決定要不要有匯出備份的 User Story，第四題是第二題答案衍生出的細節。

```
「相簿要按日期分组」         → 問：分組粒度是日、月還是年？
「重新排列这些照片」         → 問：主頁面拖放的對象是相簿、照片還是兩者？
（描述未提備份）             → 問：要不要提供備份？（答案決定 US6 是否存在）
（承第二題，拖相簿跨分組）   → 問：相簿移到別的月份後，日期要怎麼定？
```

## Bad Example
- 照片來源描述沒寫到，答案也不會增減 User Story，卻拿來問。

```
問：照片要能從雲端相簿或社群平台匯入嗎？
```

# Rule 2 - 功能描述已明說的約束不問 [MUST]
- 功能描述中已明確寫出的要求與禁止，直接當成需求推導，不再向使用者確認。

## Good Example
- 「絕不嵌套」已經明說，直接推導成需求與反向驗收情境。

```
功能描述：「相片绝对不会嵌套在其他相簿中」
→ FR-003：相簿 MUST 為單層結構
→ US2 驗收情境 6：系統不提供任何可建立巢狀相簿的操作入口
```

## Bad Example
- 把已明說的約束再問一次，浪費一題，也讓使用者以為描述沒被讀懂。

```
問：相簿是否允許放在另一個相簿裡面？
```

# Rule 3 - 不問的歧義由 AI 推定並寫入 Assumptions [MUST]
- 不符合 Rule 1 的歧義不問，由 AI 推定一個做法繼續推導，並在 Assumptions 寫出推定的內容與理由。
- 不得默默採用預設而不留紀錄。

## Good Example
- 照片能否同時屬於多個相簿沒有被問到，推定後寫明理由。

```
- **照片僅屬於一個相簿**（AI 推定）：為使「拖放移動照片」語意清楚且張數統計一致，一張照片同時只屬於一個相簿；不支援同一照片出現在多個相簿。
```

## Bad Example
- FR 寫了「每張照片僅屬於一個相簿」，Assumptions 卻沒有記錄，讀者分不出這是使用者要求還是推定。

```
- **FR-006**: 每張照片在任一時間 MUST 僅屬於一個相簿。
（Assumptions 無對應條目）
```

# Rule 4 - Assumptions 的決策來源只用兩種寫法 [MUST]
- 使用者做的決定寫「使用者於 YYYY-MM-DD 釐清選擇 X」，或「使用者於 YYYY-MM-DD 修訂，…」說明修訂內容。
- 其他一律寫「AI 推定」，不引用其他文件作為來源。

## Good Example
- 一條來自使用者的選擇，一條為推定。

```
- **日期分組粒度為「月」**（使用者於 2026-10-23 釐清選擇 A）：…
- **單一使用者、個人用途**（AI 推定）：…
```

## Bad Example
- 沒有日期，也看不出是使用者決定還是推定。

```
- **日期分組粒度為「月」**（已確認）：…
```
