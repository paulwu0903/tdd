# Rule 1 - 每個 User Story 可獨立測試 [MUST]
- 每個 User Story 完成後，不需要優先序較低的 User Story 就能驗證並交付價值。
- Independent Test 要寫出只用這個 User Story 就能完成的驗證方式。

## Good Example
- US2 只靠已匯入的照片、建相簿、加入相簿就能驗證，不需要日期分組或拖放。

```
### User Story 2 - 建立相簿並將照片整理進相簿 (Priority: P2)
**Independent Test**: 在已匯入 20 張照片的狀態下，建立 2 個相簿、將照片分別加入相簿，主頁面兩張相簿卡片的張數與封面正確，再把一張照片從一個相簿移到另一個相簿；不需要日期分組或拖放功能即可完整驗證。
```

## Bad Example
- 「建立相簿」單獨無法驗證任何價值，必須等「加入照片」完成才看得到結果。

```
### User Story 1 - 建立空相簿 (Priority: P1)
### User Story 2 - 把照片加入相簿 (Priority: P2)
```

# Rule 2 - 優先序依依賴與價值排列 [MUST]
- P1 必須單獨構成可用的 MVP；之後的 User Story 依「被誰依賴」與「價值高低」排序。
- Why this priority 要寫出這個 User Story 依賴誰、被誰依賴。

## Good Example
- 拖放需要相簿與日期分組才有對象，排在兩者之後。

```
P1 匯入照片並平鋪預覽         → 其他功能皆以它為對象
P2 建立相簿並整理照片         → 建立在 P1 之上，是 P3 ~ P5 的對象
P3 依日期分組瀏覽             → 建立在 P2 之上，是 P4 的基礎
P4 主頁面拖放重新排列相簿     → 需以 P2、P3 為前提
```

## Bad Example
- 拖放排在 P1，但沒有相簿與分組時根本沒有東西可拖。

```
P1 主頁面拖放重新排列
P2 建立相簿並整理照片
```

# Rule 3 - 功能描述的每個明確要求都由 User Story 承接 [MUST]
- 功能描述中的每一個要求，都要能對應到至少一個 User Story。

## Good Example
- 功能描述的五個要求都找得到承接的 User Story。

```
「将照片整理到不同的相簿中」                       → US2
「相簿要按日期分组」                               → US3
「在我的主页面上透过拖放来重新排列这些照片」       → US4、US5
「相片绝对不会嵌套在其他相簿中」                   → US2
「照片会以平铺式的界面进行预览」                   → US1
```

## Bad Example
- 「平鋪式預覽」沒有任何 User Story 承接，之後也不會有對應的 FR 與驗收情境。

```
「照片会以平铺式的界面进行预览」   → （無）
```

# Rule 4 - 每個 User Story 有多項驗收情境 [SHOULD]
- 每個 User Story 至少寫兩項驗收情境，涵蓋該 User Story 的主要流程。

## Good Example
- US3 用五項情境分別驗證分組、空相簿、日期自動更新、手動日期與缺拍攝日期。

```
1. **Given** 存在相簿日期分別為 2026-10-05、2026-10-20、2026-08-12 的三個相簿，**When** …
2. **Given** 一個相簿尚未加入任何照片，**When** …
（共 5 項）
```

## Bad Example
- 只有一項情境，手動日期與缺拍攝日期的行為都沒有被驗證。

```
1. **Given** 有多個相簿，**When** 使用者開啟主頁面，**Then** 相簿依日期分組。
```

# Rule 5 - 驗收情境帶具體資料值 [SHOULD]
- Given、When、Then 都寫出具體的名稱、數量或日期，讓情境能直接轉成測試。

## Good Example
- 相簿名稱、照片張數與預期結果都是具體值。

```
1. **Given** 使用者已選取 5 張照片，**When** 使用者將它們加入「東京旅行」，**Then** 相簿卡片的張數更新為 5，且相簿封面顯示其中一張照片的縮圖。
```

## Bad Example
- 「一些照片」「正確顯示」無法判定測試通過與否。

```
1. **Given** 使用者選了一些照片，**When** 加入相簿，**Then** 相簿正確顯示。
```

# Rule 6 - 禁止性約束有反向驗收情境 [MUST]
- 功能描述或推導出的「絕不」「不提供」類約束，要有一項驗收情境驗證該操作不存在。

## Good Example
- 「絕不嵌套」與「不提供還原」各有一項反向情境。

```
US2 6. **Given** 使用者嘗試在相簿內再建立相簿，**When** 使用者尋找「新增子相簿」或類似操作，**Then** 系統不提供任何可建立巢狀相簿的操作入口（相簿永遠為單層結構）。
US6 5. **Given** 使用者尋找「從備份還原」或「匯入備份檔」操作，**When** 檢視所有介面，**Then** 系統不提供任何還原入口。
```

## Bad Example
- 只有 FR 寫了 MUST NOT，沒有任何驗收情境會驗證這個操作真的不存在。

```
- **FR-003**: 相簿 MUST 為單層結構。
（US2 的驗收情境中無巢狀相關項目）
```

# Rule 7 - 驗收情境超過 10 項時檢討拆分 [SHOULD]
- 單一 User Story 的驗收情境超過 10 項時，檢討能否把其中自成一組、可獨立驗證的情境拆成依賴它的後續 User Story。
- 拆分後各 User Story 仍要符合 Rule 1、Rule 2；不拆時在 Why this priority 說明理由。

## Good Example
- 配對與對戰構成 MVP；逾時、斷線、認輸等對局保護自成一組，拆成依賴 P1 的 P2。

```
P1 以四碼房號配對並完成一局輪流猜數字對戰   → 驗收情境 10 項
P2 對局保護：回合逾時、斷線重連與認輸       → 建立在 P1 之上，驗收情境 4 項
```

## Bad Example
- 一個 User Story 塞了 16 項驗收情境，配對、對戰、逾時、斷線、認輸全擠在一起，也沒有說明為何不拆。

```
### User Story 1 - 以四碼房號配對並完成一局輪流猜數字對戰 (Priority: P1)
**Acceptance Scenarios**: 1. … 16.（共 16 項）
```

# Rule 8 - Independent Test 的資料值取自某一條驗收情境 [MUST]
- Independent Test 帶具體資料值（數量、金額、勝負、百分比）時，整組取自同一 User Story 的某一條 Acceptance Scenario，不另造一組。
- 這樣端對端測試只需要斷言一組數字，Independent Test 與情境不會各說各話。

## Good Example
- Independent Test 的 20 張照片、2 個相簿與張數，就是 Scenario 3 用的那一組。

```
**Independent Test**: 在已匯入 20 張照片的狀態下，建立 2 個相簿並分別加入 12 張與 8 張，主頁面兩張相簿卡片顯示 12 與 8（同 Scenario 3）。
3. **Given** 已匯入 20 張照片，**When** 建立「旅行」「家人」兩個相簿並分別加入 12 張與 8 張，**Then** 卡片顯示 12 與 8。
```

## Bad Example
- Independent Test 寫 30 張、3 個相簿，Scenario 3 寫 20 張、2 個相簿，兩組數字互不對應。

```
**Independent Test**: 在已匯入 30 張照片的狀態下，建立 3 個相簿各加入 10 張，卡片各顯示 10。
3. **Given** 已匯入 20 張照片，**When** 建立「旅行」「家人」兩個相簿並分別加入 12 張與 8 張，**Then** 卡片顯示 12 與 8。
```
