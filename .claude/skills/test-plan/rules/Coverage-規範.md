# Rule 1 - 每條 NFR 都要有卡，只有需要真人的 SC 可未涵蓋 [MUST]
- 範圍內的每個驗收情境、FR 與 NFR，都要出現在至少一張案例卡的「對應需求」；NFR 不能只列入未涵蓋項目，要有卡承接並進入 TDD 循環。
- 每個 SC 都要出現在某張案例卡的「對應需求」，或列入「未涵蓋項目」；只有需要真人參與（例如可用性測試、首次嘗試成功率）的 SC 可標為「未涵蓋」。
- 範圍外 User Story 專屬的驗收情境與 FR、NFR 不必列出；適用範圍包含範圍內 User Story 的全域需求要列出。
- 部分涵蓋的項目同時被卡片引用並列入未涵蓋項目。Edge Cases 透過其引用的 FR、NFR 承接，不另列。

## Good Example
- 全域 NFR-007 有量測卡承接；只有需要真人的 SC-001 列為未涵蓋。

```
### SL-035 - 100 間房同時聊天時訊息仍在 2 秒內送達
- **對應需求**: NFR-007、SC-002

## 未涵蓋項目

- **SC-001**（未涵蓋）：新玩家 30 秒內完成首次對話的成功率需要真人可用性測試；流程可行性由 SL-026 驗證。
```

## Bad Example
- NFR-007 沒有任何卡，只以「需要負載測試」為由列入未涵蓋，量化門檻永遠沒有進入 TDD 循環。

```
## 未涵蓋項目

- **NFR-007**（未涵蓋）：100 間房同時聊天需要負載測試，不在本計畫的範圍。
```

# Rule 2 - 未涵蓋項目標明狀態與原因 [MUST]
- 每一條寫成 `- **<spec 項目>**（<狀態>）：<原因>`，狀態只能是「未涵蓋」或「部分涵蓋」。
- 部分涵蓋時，寫出由哪些案例涵蓋了哪一部分、缺的是哪一部分。

## Good Example
- 部分涵蓋寫出已驗與未驗的部分。

```
- **SC-004**（部分涵蓋）：SL-033 驗證 10 次重新整理皆在 3 秒內還原，未量測 ≥ 99% 的母體比例。
```

## Bad Example
- 沒有狀態，原因空泛。

```
- **SC-004**：之後再測。
```

# Rule 3 - 變更紀錄先於測試修改 [MUST]
- 計畫進入 TDD 後發現案例有誤或缺案例時，先修改計畫並在「變更紀錄」記一筆（日期、案例、變更、原因、依據），再修改測試；涉及需求解讀的變更先詢問使用者。
- 案例 ID 進入 TDD 後不重編，新案例接續 `SL-` 的最大編號取號。
- 沒有任何變更時，變更紀錄只保留表頭與分隔列，不編造紀錄。

## Good Example
- 修正 oracle 的原因與依據都記錄下來，案例 ID 不變。

```
| 2026-10-30 | SL-005 | oracle 改為「B 的回應：`turn_timed_out` 等於 `host`」 | 原 oracle 只驗 `my_turn`，無法區分逾時是否被延長 | US1-3、FR-005 |
```

## Bad Example
- 只改了測試沒改計畫，並把新案例插在中間、後面全部重編。

```
（計畫仍是舊 oracle）
### SL-016 - 三人以上的房間不接受訊息   ← 新插入
### SL-017 - 不同房間同時送出互不干擾   ← 原 SL-016
```
