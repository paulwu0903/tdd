# Rule 1 - oracle 寫成觀察者、觀察點、比對與期望值 [MUST]
- 每條 oracle 寫成下列其中一種格式：
  - `<觀察者> 的回應：<欄位> <比對> <期望值>`（受測操作本身的回應）
  - `<觀察者> 經 <讀回入口>：<欄位> <比對> <期望值>`（經另一個入口讀回）
  - `<觀察者>：<元素> <比對>`（畫面），元素寫成 文字「…」、按鈕「…」、輸入欄「…」、連結「…」
  - `<觀察者> 的網址：<比對> <期望值>`（瀏覽器網址）
- 參數化案例的主要 oracle 與必須維持不變都寫成 `每個參數，<上述格式>`，期望值寫「該參數的期望 X」，各參數的期望值列在受測操作中；多步驟操作寫成 `步驟 (N) <上述格式>`。
- 比對只用：等於、不等於、包含、不包含、屬於、數量為、符合、可見、停用、可用、至少、至多；至少、至多只用於數量與比例的門檻。
- 時間門檻寫成 `N 秒內可見（自 <起算事件> 起算）`。

## Good Example
- 每條都寫出誰、從哪裡觀察、比什麼。

```
  - B 的回應：status code 等於 200
  - A 經 `GET /rooms/{room_id}`：`winner` 等於 `challenger`
  - A：文字「你落敗了」2 秒內可見（自 B 的「你獲勝了」可見起算）
```

## Bad Example
- 沒有觀察者與觀察點，比對用語模糊，時間沒有起算點。

```
  - 回傳成功
  - 房間正確關閉
  - A 很快看到結果
```

# Rule 2 - oracle 確定且可經公開介面觀察 [MUST]
- 寫出確切的欄位名、列舉值與畫面文字，不寫「狀態正確」「顯示提示」這類需要猜名稱的描述。
- 名稱與文字的來源依序為：spec 的明文、repo 既有的實作、自行訂定；spec 中含情境代號的句子（例如「B 回合逾時」的 B）不算明文；自行訂定的名稱在最後的回報中列出。不同狀態不使用同一段文字，避免 oracle 在錯誤的狀態下也成立。
- 每條 oracle 只有一個期望結果，不用「或」並列兩種可接受的結果；值本身是集合時用「屬於 {…}」。
- 只寫能經由公開介面觀察的結果；觀察不到的（例如「沒有建立任何房間」但沒有列表入口）改寫成可觀察的形式，否則不收錄。

## Good Example
- 名稱確切、結果唯一。

```
  - B 經 `GET /rooms/{room_id}`：`closed_reason` 等於 `host_left`
  - A 的回應：status code 屬於 {404, 405}
```

## Bad Example
- 名稱要猜；用「或」並列兩種結果；第三條無法經公開介面觀察。

```
  - B 看到房間關閉的原因
  - A：開局按鈕不可用，或顯示等待對手準備
  - 資料庫中沒有新增房間
```

# Rule 3 - 不變條件獨立列出 [MUST]
- 「必須維持不變」只寫 Act 之後應該保持原樣的狀態，例如被拒絕後狀態未改、無效猜測後紀錄仍為空；用同樣的 oracle 格式，多條以「；」分隔。
- 主要 oracle 只寫 Act 預期造成的結果；沒有不變條件時寫「無」。

## Good Example
- 被拒絕的開局，預期結果是 409，不變條件是狀態仍為 preparing。

```
- **主要 oracle**:
  - A 的回應：status code 等於 409
- **必須維持不變**: A 經 `GET /rooms/{room_id}`：`status` 等於 `preparing`
```

## Bad Example
- 不變條件混在主要 oracle 中，讀者分不出哪條是預期改變、哪條是副作用檢查。

```
- **主要 oracle**:
  - A 的回應：status code 等於 409
  - A 經 `GET /rooms/{room_id}`：`status` 等於 `preparing`
- **必須維持不變**: 無
```

# Rule 4 - 寫出要抓的錯誤實作 [MUST]
- 「要抓的錯誤實作」寫一個實際可能發生的錯誤實作，且至少一條主要 oracle 或不變條件會因它而失敗。
- 錯誤實作要具體到能想像成程式碼，不寫「功能壞掉」。

## Good Example
- 錯誤實作具體，oracle「A 的房間恰好 1 位 challenger」會因它失敗。

```
- **要抓的錯誤實作**: 「查詢等待中房間」與「寫入挑戰者」之間沒有加鎖，兩位以上玩家被寫入同一個房間。
```

## Bad Example
- 錯誤實作空泛，也沒有任何 oracle 能對應。

```
- **要抓的錯誤實作**: 配對有 bug。
```

# Rule 5 - 測試資料合法且期望值有推導 [MUST]
- 測試資料必須符合被測規則以外的所有規則，例如測併發配對時，每組配對碼本身都是合法的四碼。
- 期望值來自規格或手算，不直觀的期望值在括號中附推導。

## Good Example
- 配對碼皆合法；期望值附手算推導。

```
- **受測操作**: 8 位玩家同時各以一碼配對：`1234`、`2345`、`3456`、`4567`、`5678`、`6789`、`7890`、`8901`（皆為 4 個互不相同的數字）。
  - A：文字「9120：1A3B」可見（9 位置相同；0、1、2 存在但位置不同）
```

## Bad Example
- 測併發卻用了 `2234` 這種本身不合法的碼，失敗原因是格式驗證而不是併發；期望值沒有推導。

```
- **受測操作**: 8 位玩家同時各以一碼配對：`1234`、`2234`、`3234`……
  - A：文字「9120：1A3B」可見
```

# Rule 6 - 重複量測的 oracle 寫成全數或比例門檻 [MUST]
- 受測操作重複 N 次或量測多筆時，oracle 寫成 `N <單位>中，<達標條件>者：數量為 N`，要求每一次都達標。
- spec 只要求比例時，寫成 `全部 <單位>中，<達標條件>者所占比例：至少 <比例>`；計時的起訖點寫在該卡的量測條件，不在每條 oracle 重寫起算點。

## Good Example
- 全數達標與比例門檻各自寫成可計數的形式。

```
  - 20 則訊息中，送達時間在 2 秒內者：數量為 20
  - 全部訊息中，送達時間在 2 秒內者所占比例：至少 0.95
```

## Bad Example
- 只量平均值，一次 5 秒的延遲會被其他次數平均掉；比例沒有門檻比對。

```
  - 20 則訊息的平均送達時間：等於 2 秒內
  - 全部訊息中，大多數在 2 秒內送達
```
