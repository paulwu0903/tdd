# Rule 1 - 只問上游未決定且會改變觀察 seam 或測試層級的決策 [MUST]
- 要問使用者的測試決策必須同時符合兩點：research.md、techstack.md、plan.md 與 `analysis/` 都沒有決定，且答案會增減觀察 seam 或改變某個觀察 seam 的測試層級（例如 E2E 或 unit、是否測到資料庫）。
- 上游或使用者已明說的測試決策直接採用，不再確認；上游的字面能讀成兩種觀察 seam 或層級的，視為未決定，要提問。
- 工具選擇、資料隔離方式、時限數值等其餘決策由 AI 推定，不提問。

## Good Example
- research.md 的測試工具只寫了 E2E，沒有決定後端要不要另以 API seam 測到資料表，這會增減觀察 seam，因此提問。

```
research.md `R4. 測試與品質工具`：子段 `› E2E`（Playwright，Chromium）
問：後端規則細節要另以 API seam 驗證並測到 `chat_messages 資料表介面` 嗎？A. 只以 UI seam 驗證；B. 另立 API seam，經真實 MySQL 驗證。
```

## Bad Example
- 測試工具已由 research.md 決定，又不會改變觀察 seam 或層級，卻拿來問；API seam 的層級上游已寫明，又再問一次。

```
research.md `R4. 測試與品質工具`：子段 `› API E2E`（pytest + httpx，真實 MySQL）、`› E2E`（Playwright，Chromium）
問：前端要用 Playwright 還是 Cypress？
問：API 測試要不要打到資料庫？
```

# Rule 2 - AI 推定的決策在回報中列出 [MUST]
- 由 AI 推定的測試決策不寫進 test-plan.md，改在最後的回報中逐條列出，讓使用者能事後否決。

## Good Example
- 推定的決策列在對話回報中。

```
回報：
- AI 推定：前端以 Playwright 執行，雙人情境用兩個 browser context。
- AI 推定：時限以啟動時注入的短時限搭配真實等待驗證，不替換時鐘。
```

## Bad Example
- 推定的決策寫進計畫的獨立章節，計畫混入決策脈絡。

```
## Assumptions
- **前端以 Playwright 執行**（AI 推定）：……
```
