# Rule 1 - 一張卡只驗一個行為 [MUST]
- 每張卡只驗一個行為，寫進「唯一測試意圖」，一句話說完。
- 前置條件與受測操作完全相同、只是觀察點不同的情境，合併成一張卡、多條 oracle。
- 驗證同一行為、只差在資料值（包括前置狀態中的資料值）的情境，寫成同一張卡的參數化；行為、受測入口或前置狀態的種類不同時，分成不同的卡。
- 「本案例不驗證」寫出最接近、最容易被順手一起驗的那個相鄰行為。

## Good Example
- 意圖只有一個；「A 看到我：」與「B 2 秒內看到對手：」是同一個操作的兩個觀察點，合成一張卡；相鄰行為寫進不驗證。

```
- **唯一測試意圖**: 準備中 A 送出訊息，A 看到「我：」、B 不重新整理也在 2 秒內看到「對手：」與送出時間。
- **本案例不驗證**: 沒有訊息時的空狀態。
```

## Bad Example
- 一張卡塞進送出、拒絕空白與空狀態三個行為，失敗時看不出是哪個行為壞了。

```
- **唯一測試意圖**: 聊天室的送出、空白拒絕與空狀態都正常。
```

# Rule 2 - 判定案例類型 [MUST]
- 一律假設從零開始、依本計畫的順序實作，不看 repo 現況；以「排在前面的案例都實作完成後，這張卡是否已會通過」判定為下列之一：

| 案例類型 | 判準 |
|---|---|
| `TDD Slice` | 需要新增或修改實作才會通過，預期先紅 |
| `防回歸（預期不先紅）` | 前面案例的實作已讓它通過，用來防止日後退化，例如「送出訊息不消耗回合」 |
| `旅程（預期不先紅）` | 跨多個行為的完整流程，各步驟已由前面的案例實作 |
| `NFR 量測` | 驗證一條 NFR 的量化門檻，須在量測條件下重複或加壓執行；與 TDD Slice 一樣進入 TDD 循環 |

## Good Example
- 訊息與猜測分屬不同入口的實作在前面的案例已完成，「送出訊息不消耗回合」寫完就會通過，標為防回歸。

```
### SL-004 - 送出訊息不消耗回合也不新增猜測

- **案例類型**: 防回歸（預期不先紅）
```

## Bad Example
- 每張卡都標 TDD Slice，新 session 遇到一寫就過的測試會誤以為 Red 失敗。

```
### SL-004 - 送出訊息不消耗回合也不新增猜測

- **案例類型**: TDD Slice
```

# Rule 3 - 測試名稱帶案例 ID [MUST]
- 測試名稱以英文描述 WHAT，並依觀察 seam 的測試慣例帶入案例 ID：函式式寫成 `test_sl_<三位數>_<snake_case 描述>`，字串標題式寫成 `<ID> <描述>`。
- repo 既有測試沒有帶 ID 時，計畫仍依此規則命名，由 TDD 實作時改名。
- 「測試檔」寫出該測試所在的檔案路徑，取自 plan.md 的 Source Code 樹中對應該觀察 seam 的測試檔，不自行新增路徑。

## Good Example
- 兩種慣例都帶著 ID，可以直接用 ID 搜尋；測試檔都是 plan.md Source Code 樹中已列出的檔案。

```
- **測試名稱**: `test_sl_003_messages_during_game_are_listed_in_send_order`
- **測試檔**: `backend/tests/test_chat.py`
- **測試名稱**: `SL-001 a message sent while preparing appears for both players with sender labels`
- **測試檔**: `frontend/e2e/chat.spec.ts`
```

## Bad Example
- 沒有 ID，描述的是 HOW；測試檔是 Source Code 樹中沒有的路徑。

```
- **測試名稱**: `test_post_message_inserts_row_into_chat_messages`
- **測試檔**: `backend/tests/chat/test_post_message.py`
```

# Rule 4 - 受測部位寫到能在程式中定位 [MUST]
- 受測部位只寫受測操作那一步實際操作的單一入口；參數會打到不同入口時，依 Rule 1 分成不同的卡；受測操作是「不做任何操作」或「讀取」時，寫觀察結果的那個入口。依觀察 seam 的類型使用下列寫法：

| 觀察 seam 類型 | 寫法 |
|---|---|
| HTTP API | `` `METHOD /path` `` |
| Web UI | `` `路由` · 元件「名稱」 `` |
| repository／模組 | `` `module.Class.method()` `` |
| CLI | `` `command --flag` `` |
| 智能合約 | `` `module::function` `` |

## Good Example
- 直接指到 endpoint 與 UI 元件。

```
- **受測部位**: `POST /rooms/{id}/messages`
- **受測部位**: `/rooms/[id]` · 按鈕「送出訊息」
```

## Bad Example
- 只寫功能區塊，讀者不知道要呼叫哪個入口。

```
- **受測部位**: 房間的聊天功能。
```

# Rule 5 - 受測操作只有一個被測行為 [MUST]
- 受測操作寫出 Act 的具體輸入值，例如 request body、填入的文字、按下的按鈕。
- 一般只有一個操作；只有「順序本身就是被測行為」時才寫多步驟，以 (1)(2)… 編號，需要等待畫面出現的步驟寫「等到 <可觀察結果>」，等待本身不是 oracle。
- 參數化的操作寫成 `<參數 id>：<值>`，每組參數各列一次。
- 受測行為是時間經過或畫面呈現時，受測操作寫成「<觀察者> 不做任何操作，持續 N 秒」或「讀取 <觀察者> 的 <元素>」。

## Good Example
- 多步驟只用在一來一往這種順序本身就是行為的情境；參數化寫出 id 與值。

```
- **受測操作**: 依序操作，順序本身是受測行為：(1) A 在「訊息」填入 `哈囉` 並按「送出訊息」；(2) 等到 B：文字「對手：哈囉」可見；(3) B 在「訊息」填入 `你好` 並按「送出訊息」。
- **受測操作**: A 以下列參數各送出一次：`blank`：`"   "`（期望 detail「訊息不可為空白」）、`empty`：`""`（期望 detail「訊息不可為空白」）、`too_long`：`"字" * 201`（期望 detail「訊息最多 200 字」）。
```

## Bad Example
- 把開房、配對、送出都塞進受測操作，Act 不只一個行為；輸入值也沒寫。

```
- **受測操作**: A 開房、B 配對，然後 A 送出一則訊息並重新整理。
```

# Rule 6 - 前置條件寫狀態，建立方式寫做法 [MUST]
- 前置條件寫出 Act 之前的可觀察狀態與具體值（房間狀態、答案、輪到誰、已有的訊息），不寫「本次 request 尚未送出」這類套話。
- 建立方式寫出 Fixture helper 的實際呼叫與參數，以及卡片專屬的額外步驟；只在這張卡注入的時限設定、等待秒數、網路中斷或延遲等環境做法直接寫在這裡。

## Good Example
- 前置條件是帶值的狀態；建立方式是能直接照寫的呼叫，時限寫在卡內。

```
- **前置條件**: 回合時限 1.5 秒；對局 `status` 等於 `playing`，輪到 A；A 在回合開始後 0.8 秒送出「再等我一下」，之後未提交猜測。
- **建立方式**: `start_server(Timeouts(turn_seconds=1.5, disconnect_seconds=600, waiting_seconds=600))` → client；`started_game(client, "5678", "9012")` → `(room_id, A, B)`，記下開局時刻 t0；等到 t0 + 0.8 秒；`send_message(client, room_id, A, "再等我一下")`；等到 t0 + 1.8 秒
```

## Bad Example
- 前置條件沒有值且混入套話；建立方式引用卡外未定義的設定名稱。

```
- **前置條件**: 遊戲進行中；本次 request 尚未送出。
- **建立方式**: 依 TURN 設定檔啟動，進入對局後送一則訊息。
```

# Rule 7 - 特定需求類型要有對應案例 [MUST]
- 「絕不」「不提供」類需求要有反向案例，驗證該操作或入口不存在。
- 時限類需求以短時限加真實等待驗證；每一種會重新計時的時限，至少有一張驗證重新計時的案例。
- 併發類需求同時涵蓋「同一資源」與「不同資源」兩種案例。
- spec 或使用者要求資料持久化時，要有「重新啟動後讀回」的案例，對應需求寫該條 spec 項目或「使用者需求：資料持久化」。

## Good Example
- 併發同時涵蓋同一房間與不同房間。

```
SL-015 同一房間雙方同時送出時每則恰好保存一次且順序一致
SL-016 不同房間同時送出互不干擾
```

## Bad Example
- 只測同一房間的併發，鎖範圍過大造成的房間互相干擾無人發現。

```
SL-015 同一房間雙方同時送出時每則恰好保存一次且順序一致
（無不同房間的併發案例）
```

# Rule 8 - 依依賴排序且卡片自足 [MUST]
- 案例依 User Story 優先序分組；組內依依賴排序，每張卡的前置狀態與不變條件都必須能由排在它前面的案例實作出來。
- 案例 ID 以 `SL-` 從 001 起全檔連號，不依觀察 seam 或 User Story 重新起算。
- 卡片不引用其他案例卡的 ID；需要共用的前置狀態一律透過 Fixture。

## Good Example
- 「被拒絕的訊息顯示原因」以空狀態提示作為不變條件，排在空狀態案例之後。

```
### SL-002 - 沒有任何訊息時顯示空狀態提示
### SL-008 - 被拒絕的訊息在畫面上顯示原因
```

## Bad Example
- 排在空狀態案例之前，做到這張卡時不變條件的提示文字還不存在；並引用其他卡。

```
### SL-001 - 被拒絕的訊息在畫面上顯示原因
- **建立方式**: 同 SL-002 的房間
```

# Rule 9 - 切片卡垂直穿過行為經過的所有層 [MUST]
- 一張切片卡驗一個行為從受測入口一路穿過它經過的所有層（例如畫面、API、資料表），不把同一個行為拆成前端、API、repository 各一張卡。
- 卡片直接列在所屬 User Story 之下，不以前端、API、repository 分組。
- 旅程卡保留給跨多個行為的完整流程，不用來承接單一行為。

## Good Example
- 同一個「送出訊息雙方都看到」的行為，一張卡從畫面穿過 API 到資料表。

```
## User Story 1 - 同房玩家在準備與對戰時即時傳送文字訊息

### SL-001 - 準備中送出的訊息雙方都看得到並標示發送者

- **涉及系統介面**: `聊天室介面`、`聊天 API 介面`、`chat_messages 資料表介面`
```

## Bad Example
- 同一個行為依層拆成三張卡並以層分組，任一層通過都不代表行為成立。

```
## 測試案例 - 前端
### SL-001 - 聊天室顯示送出的訊息
## 測試案例 - API
### SL-002 - POST /rooms/{id}/messages 回 201
## 測試案例 - Repository
### SL-003 - 訊息寫入 chat_messages
```

# Rule 10 - 標出觀察 seam 與涉及系統介面 [MUST]
- 「觀察 seam」寫一個依 `rules/觀察seam-規範.md` 定出的 seam：業務規則的細節（參數組合、邊界、權限、併發）用 API，使用者可見的呈現與流程（畫面文字、停用狀態、即時同步）用 UI；spec 明定要顯示給使用者的文字屬於呈現。
- 同一組規則細節只在一個 seam 驗一次，另一個 seam 只驗一組代表值的呈現。
- 「涉及系統介面」以反引號列出這張卡穿過的全部系統介面，名稱逐字取自 plan.md 的系統介面盤點。

## Good Example
- 拒絕的三組參數在 API 驗；畫面只用一組空白驗呈現。介面名稱與盤點一致。

```
### SL-007 - 空白與過長的訊息被拒絕
- **觀察 seam**: API
- **涉及系統介面**: `聊天 API 介面`

### SL-008 - 被拒絕的訊息在畫面上顯示原因
- **觀察 seam**: UI
- **涉及系統介面**: `聊天室介面`
```

## Bad Example
- 畫面再把三組拒絕參數各跑一次，與 API 重複；介面名稱是自創的，不在盤點中。

```
### SL-008 - 被拒絕的訊息在畫面上顯示原因（blank、empty、too_long 三組參數）
- **觀察 seam**: UI
- **涉及系統介面**: `聊天前端`、`訊息後端`
```

# Rule 11 - NFR 量測卡寫出量測條件 [MUST]
- 驗證 NFR 量化門檻的卡標為 `NFR 量測`，在「受測操作」之後加上「量測條件」，寫出負載形狀、重複次數與每次量測的起訖點。
- 「量測條件」只出現在 NFR 量測卡；其他類型的卡不寫此欄位。

## Good Example
- 負載形狀、次數與起訖點都寫在量測條件，oracle 只寫門檻。

```
- **案例類型**: NFR 量測
- **受測操作**: A 重新整理頁面 10 次，每次等到「對手：m30」可見後才進行下一次。
- **量測條件**: 房內 30 則訊息；每次量測自 A 觸發重新整理起，至「對手：m30」可見止的時間。
```

## Bad Example
- 沒有量測條件，讀者不知道房內有幾則訊息、量幾次、從哪裡計時到哪裡。

```
- **案例類型**: NFR 量測
- **受測操作**: A 重新整理頁面。
- **前置條件**: 房內有一些訊息。
```

# Rule 12 - 旅程與 NFR 量測卡依範圍放置 [MUST]
- 只涉及單一 User Story 的旅程卡與 NFR 量測卡，寫在該 User Story 之下。
- 涉及兩個以上 User Story 的旅程卡，寫在 `## 跨故事旅程`；該段只放旅程卡。
- 驗證全域 NFR 的量測卡，寫在 `## 全域 NFR`；該段只放 NFR 量測卡。

## Good Example
- 跨 US1 與 US2 的旅程放在跨故事旅程；全域 NFR-007 的量測放在全域 NFR。

```
## 跨故事旅程
### SL-034 - 從開房聊天、換挑戰者到賽後檢視的完整旅程
- **對應需求**: US1-1、US2-2、US2-4、FR-001、FR-009、FR-010

## 全域 NFR
### SL-035 - 100 間房同時聊天時訊息仍在 2 秒內送達
- **對應需求**: NFR-007、SC-002
```

## Bad Example
- 全域 NFR 的量測卡塞在 US1 之下；跨故事旅程段混入一張防回歸卡。

```
## User Story 1 - 同房玩家在準備與對戰時即時傳送文字訊息
### SL-025 - 100 間房同時聊天時訊息仍在 2 秒內送達
- **對應需求**: NFR-007

## 跨故事旅程
### SL-034 - 後端重啟後聊天紀錄完整讀回
- **案例類型**: 防回歸（預期不先紅）
```
