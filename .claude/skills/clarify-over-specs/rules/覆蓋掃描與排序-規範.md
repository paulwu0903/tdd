# Rule 1 - 十類逐類掃描 [MUST]
- 每次掃描 spec.md 都要走完下表十類，每類各給一個狀態，不得只掃有寫到的區塊。
- 掃描時以 spec.md 的 User Story、Acceptance Scenarios、FR / NFR、Edge Cases、Key Entities、Success Criteria、Assumptions 為對照，判斷該類的檢查項是否被回答。

| 類別 | 檢查項 |
|---|---|
| Functional Scope & Behavior | 核心使用者目標與成功條件、明確的 out-of-scope、角色 / persona 區分 |
| Domain & Data Model | 實體、屬性、關係；識別與唯一性規則；生命週期 / 狀態轉移；資料量假設 |
| Interaction & UX Flow | 關鍵使用者旅程、錯誤 / 空白 / 載入狀態、無障礙或在地化 |
| Non-Functional Quality Attributes | 效能、擴展性、可靠性與可用性、安全與隱私、合規 |
| Integration & External Dependencies | 外部服務與其失敗模式、匯入 / 匯出格式 |
| Edge Cases & Failure Handling | 負面情境、頻率限制、衝突處理（如並行編輯） |
| Constraints & Tradeoffs | 已明示的取捨與被否決的替代方案 |
| Terminology & Consistency | 正規用語、同義詞或棄用詞是否混用 |
| Completion Signals | 驗收情境可測性、可量化的 Definition of Done |
| Misc / Placeholders | TODO 標記、未決決策、未量化的形容詞（robust、intuitive） |

## Good Example
- 十類各有一個狀態，連 spec.md 沒有專屬區塊的 Terminology 與 Completion Signals 也被判定。

```
Functional Scope & Behavior ........ Clear
Domain & Data Model ................ Partial
Interaction & UX Flow .............. Missing
Non-Functional Quality Attributes .. Partial
Integration & External Dependencies  Clear
Edge Cases & Failure Handling ...... Clear
Constraints & Tradeoffs ............ Clear
Terminology & Consistency .......... Partial（「主管」與「審核人」混用）
Completion Signals ................. Clear
Misc / Placeholders ................ Missing（FR-004 寫「快速回應」未量化）
```

## Bad Example
- 只掃了 FR 與 Edge Cases 兩個區塊就下結論，其餘八類沒有狀態。

```
FR 區塊 ........ 看起來完整
Edge Cases ..... 有三條
結論：無需澄清
```

# Rule 2 - Clear / Partial / Missing 的判準 [MUST]
- Clear：該類每個檢查項在 spec.md 都有明確、可測的敘述，或已在 Assumptions 以「使用者於 YYYY-MM-DD 釐清選擇 X」或「使用者於 YYYY-MM-DD 修訂」寫明。
- Partial：有提到但不足以據此設計或驗收，例如只用形容詞、只覆蓋部分檢查項、兩處敘述互相衝突；或在 Assumptions 以「AI 推定」寫明、尚未經使用者拍板。
- Missing：spec.md 與 Assumptions 都沒有觸及該檢查項。
- AI 推定進入候選後與其他缺口一同依 Rule 5 排序，不另設優先；影響低者列 Outstanding 不問。

## Good Example
- 「30 秒內」可量化為 Clear；使用者釐清過的為 Clear；「快速回應」有提到但無法驗收為 Partial；AI 推定的審核層數尚未拍板為 Partial；完全沒寫斷線處理為 Missing。

```
NFR-002：主管審核頁 MUST 在 30 秒內顯示最新申請              → Clear
Assumptions：- **單層審核**（使用者於 2026-10-24 釐清選擇 A） → Clear
FR-004：系統 MUST 快速回應使用者操作                          → Partial
Assumptions：- **逾期 7 天提醒**（AI 推定）                   → Partial（候選，依 Rule 5 排序）
（spec 與 Assumptions 均未提到使用者中途斷線）                 → Missing
```

## Bad Example
- 「逾期 7 天提醒」只是 AI 推定，卻因為寫在 Assumptions 就被標成 Clear，使用者永遠沒有機會拍板這個會影響通知流程的決策。

```
Assumptions：- **逾期 7 天提醒**（AI 推定） → Clear
```

# Rule 3 - 剔除不該問的缺口 [MUST]
- 下列缺口不列為候選：實作方法、tech stack 比較、task breakdown、spec.md Assumptions 已由使用者拍板者、純風格偏好（文案、配色、命名）。
- 只保留答案會實質改變架構、資料模型、測試設計、UX 行為、營運就緒或合規驗證的缺口。

## Good Example
- 「同一員工能否重複送出重疊假期」會改變資料模型與驗收測試，保留；「資料庫選型」屬 tech stack，剔除；「送出按鈕文案」屬風格偏好，剔除。

```
保留：重疊假期是否允許重複申請？
剔除：請假紀錄要存 PostgreSQL 還是 MySQL？
剔除：送出按鈕要寫「提交」還是「送出」？
```

## Bad Example
- Assumptions 已寫「使用者於 2026-10-24 釐清選擇單層審核」，仍把審核層數列為候選缺口。

```
Assumptions：- **單層審核**（使用者於 2026-10-24 釐清選擇 A）：…
候選缺口：審核流程是單層還是雙層？
```

# Rule 4 - 技術選型標 Deferred，只問需求行為 [MUST]
- 技術性類別（Integration、Constraints、NFR 中的實作手段）只掃「會改變使用者可觀察行為」的部分；純技術選型一律標 Deferred，並在完成報告註明交給 technical-research。
- 判準：答案寫進 spec.md 後仍是 WHAT / WHY 的敘述才可問；答案是 HOW（框架、協定、儲存、部署）即 Deferred。

## Good Example
- 外部 Email 服務失敗時使用者看到什麼是需求行為，可問；要用哪家 Email 服務是技術選型，Deferred。

```
可問：Email 通知送出失敗時，申請人會看到什麼、系統是否重送？
Deferred（→ technical-research）：Email 服務要用 SES 還是 SendGrid？
```

## Bad Example
- 把技術選型當成 Integration 類的缺口提問，答案寫進 spec.md 會變成 HOW。

```
候選缺口：即時通知要用 WebSocket 還是 SSE？
```

# Rule 5 - Impact × Uncertainty 排序 [MUST]
- 候選缺口依「答案改變下游設計與驗收的幅度 × 目前不確定程度」由高到低排序，最高者先問。
- 不得以兩題低影響缺口取代一題高影響缺口；高影響類別未解完前，低影響類別不進入本輪。

## Good Example
- 權限模型影響資料表、API 與測試，且 spec 完全沒寫，排第一；錯誤訊息語氣影響小，排最後。

```
1. 誰能查看他人請假紀錄？（Functional Scope；Impact 高 × Uncertainty 高）
2. 假期重疊是否允許？（Domain & Data；Impact 高 × Uncertainty 中）
3. 錯誤訊息要正式還是口語？（Interaction & UX；Impact 低 × Uncertainty 高）
```

## Bad Example
- 兩題低影響先問完，權限模型這題被擠出 5 題預算。

```
1. 錯誤訊息要正式還是口語？
2. 列表每頁顯示幾筆？
…（第 6 題才輪到）誰能查看他人請假紀錄？
```
